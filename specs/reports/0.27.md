# PT/FM 0.27

The work in this version, task by task: why it was done and how, with the commits that hold its code. The changes
in short, a line each: [CHANGELOG.md](../../CHANGELOG.md).

## The changelog

**Why.** The changes from one version to the next had no place of their own but the commit messages, which are
written for the code, not for the people who use PT/FM.

**How.** `CHANGELOG.md` at the repository's top: each change one entry in plain words, its kind first (FEATURE,
CHANGE, BUG, REMOVED). The top section, Next version, collects the changes since the last release; at a release it
takes the version's number and a new Next version starts above it. Every change a user would notice goes in as it is
made (`AGENTS.md`); the README and the layout name the file.

**Commits:** `01e5467`.

## The EDITOR's WRITE when only an emptied FM-1 fits

**Why.** WRITE makes the FM-1 hold exactly what its panel shows. It places the panel's records around what stays on
the FM-1: records already equal are left where they are, and blocks still taken by deleted records' headers count as
taken. So a panel that fits the user area could find no room around them, and WRITE refused it. The uploaders (the
install page, the emulator) already offered REPLACE ALL for the same case.

**How.** WRITE still plans in place first, so equal records stay and a write is short. When that plan does not fit
but the panel fits the user area emptied, it takes the uploaders' clean plan instead and writes the whole user area
anew. Its dialog says so before writing (the blocks written and erased) and names what the FM-1 loses as removed, so
BACKUP FIRST reads those onto the TABLE; records the page cannot read are read from the FM-1 first and written back as
they were. Only a panel larger than the user area is refused now.

**Tested** on the PC: the editor's device test, with a virtual FM-1 whose free room is pinned by deleted records'
headers (the layout, what is named removed, an unreadable record back byte for byte), and a page scenario in a
headless Chrome that writes such a panel. Not yet tried with a real FM-1.

**Commits:** `01e5467`.

## The site's pixel fonts

**Why.** On the landing, words in the FM-1's screen font came apart ("MI DI", "TI ME"), and the logo and the figures
sat a pixel or two to the left. The site's two pixel fonts, made from Terminus, gave every letter a left side bearing
of 0 while its outline began at its first lit column; browsers place the outline by the side bearing, so each letter
was drawn as far left as its blank columns: I, l and 1 two pixels, E and D one.

**How.** The font tool (`site/tools/pixfont.py`) sets each glyph's side bearing where its ink starts. Both fonts were
built again; only the side bearings differ (outlines, advances and characters as they were), so every letter sits in
its cell as Terminus draws it.

## FAVORITES: the design

**Why.** Players reach for the same few instruments across many cartridges, and browsing cartridge by cartridge to
find them is slow on the FM-1's knobs.

**How.** A new cartridge kind holding **references**, not copies: each slot names an instrument elsewhere
(`0B:05`). That one choice keeps songs safe: whatever is played, recorded or written carries the instrument's own
number, so nothing ever refers to a favourites list and a list can be reordered, emptied or deleted freely. A copy
would have made songs depend on the list and doubled the room every favourite takes. The rest follows from it:
- the cursor's place (`FB:07`) and the current instrument (`0B:05`) are kept apart, and on an empty or missing
  favourite the instrument stays the last one picked, so the keys never go silent and REC never writes a
  favourites number;
- a built-in, empty FAVORITES at `FB` exists from the first start, the user's own made with NEW; FAVORITES comes
  first in every cartridge list, MIDI's bank select included, and **SEL + GLO** (SEL held first, so GLO alone stays
  instant) jumps there and back (it was SEL + ENV at first: on the FM-1 SEL and ENV sit side by side and two
  neighbours are hard to press together; GLO stands apart, combined with SEL nowhere, and SEL's hold layer lists it);
- **GLO held + PRESETS** picks a favourite once: the keys' instrument becomes its source while the current cartridge
  and slot stay, so PRESETS alone goes on from them; the favourites show while GLO is held. It shares SEL + GLO's
  "favourite last used". Not on INSTRUMENTS, where the cursor is the current instrument and a pick that left it would
  split the two. GLO gets a hold layer for it, so GLO held past the hold delay and let go no longer opens the
  properties (as every button with a layer); GLO tapped still acts at once, the knob counting in the order it came;
- EDIT changes which instrument a favourite points at, with the cartridge and instrument lists shown while the
  knobs turn; the instrument itself is edited in its own cartridge;
- favourites join the references rules: MOVE and SWAP rewrite them; a DELETE leaves them naming the place
  (`MISSING`, grey as every reference to nothing, silent), so they play again once something is put there; CLEAN
  UP counts them as uses; CHECK REFERENCES lists the broken ones;
- a firmware too old to know the kind keeps its records but may reuse a favourites cartridge's number; then the
  other cartridge always wins and the favourites record is dropped, so a sound cartridge is never lost to a list of
  references;
- the EDITOR page edits the kind too, takes the named cartridges along when moving it, and never deletes a
  favourites list with what it names, nor its sources with it.

**Checked.** The design was read four times against the specs before it was settled; each pass found real conflicts
(the references rules, compaction rewriting records as newer saves, the help's line limits, the menus' level rules,
the footer and list layouts), all resolved in the proposal, `specs/proposals/202610311523-favorites.md`.

**Commits:** to be added once committed.

## The EDITOR page's recorder and cutting samples: the design

**Why.** Making a sample meant recording elsewhere and dropping the file in. Recording straight into the EDITOR
page, from a microphone, a line in or the FM-1 itself over USB audio, closes that loop; and a recording of several
hits is most useful cut apart.

**How.**
- **The recorder** keeps one take at a time, the next replacing it, and only SAVE puts a take on the TABLE, so trying
  again costs nothing. A take is kept whole as the sample's original and its sample made at the best a sample on the
  FM-1 can be (16 bits, 44.1 kHz); making it smaller is left to the SAMPLE tab's OPTIMIZE. Recording has no length
  limit; a sample too long for the FM-1's 20-bit length stays on the TABLE marked `TOO LONG` until cut or lowered.
- **The SAMPLE tab's cut becomes a selection** with an explicit TRIM, which lets a part be saved as a new sample
  while the sample itself stays as it is. New samples are named from the sample's name with two digits, the first
  free.
- **SLICES** finds the hits (a jump in level, measured in 5 ms windows, with a sensitivity), marks silent spans
  against a level 40 dB under the loudest peak (a fixed level would count a microphone's noise as sound; TRIM
  SILENCE uses the same level, OPTIMIZE's LOSSLESS keeps its own), and then removes silence or chosen slices with
  short crossfades, saves slices as samples, or **makes a kit**: a sampler cartridge with a slice in each slot and a
  FUSION kit with a slice on each key from C-4 up, each hit ringing out after its key is let go through a parameter
  command in its cell, as the demo disk's drum kit does (an envelope that never releases would have left the notes
  sounding in songs).
- Originals get a store of their own in the browser, written once, so long recordings are not rewritten at every
  change of the page.

**Checked.** Four reads against the specs and the page's code before it was settled (the cut already trimming as it
was dragged, the 20-bit length refused by the importer, the preview's 1 MB room, how the demo kit really rings, the
page's storage), all resolved in the proposal, `specs/proposals/202610311701-editor-recorder.md`.

**Commits:** to be added once committed.

## The EDITOR page's instruments, references to nothing and deleting built-ins: the design

**Why.** A cartridge tab on the EDITOR page edited one instrument at a time and moved none, so gathering
instruments from several cartridges or putting one in order meant rebuilding it slot by slot. And the built-in
cartridges filled every list, wanted or not.

**How.**
- **Many at once:** a tab lists every slot and selects many (click, Shift, Ctrl, the keys, taps); COPY, CUT, PASTE,
  REPLACE and DELETE work on the selection, between any two cartridges of one type, on either panel. The clipboard
  holds contents, not places (a sample, a FUSION pattern, a favourite's source come along), so a paste is the same
  whatever happens to the originals meanwhile.
- **PASTE only adds,** into empty slots, all or nothing; **REPLACE** is the one way to put another instrument in a
  place songs play. Kept apart, a paste never changes how a song sounds.
- **Rearranging moves the references with the instruments:** a drag, MOVE TO or Alt+↑ ↓ moves slots, and every
  cell, loop and favourite that named a place, and the settings' current instrument, follow at SAVE, so everything
  sounds as before. A move onto an empty place is a swap with it, on the FM-1 too, so references that still name
  that place keep pointing at nothing rather than waking up.
- **DELETE never rewrites a reference.** What named a deleted thing keeps naming its place, drawn grey, and plays
  as a **silent engine**: an ordinary cell, every rule and command working, whose note sounds nothing. Rewriting
  references on DELETE, as the FM-1 offered before, took the instrument out of cells and so changed what the notes
  after them played; keeping the place changes nothing else in the song. An instrument put in that place later
  plays there again, and new numbers pass over places references still name, so that happens only when meant.
- **CLEAN UP's MISSING REFERENCES** clears such references when asked: favourites emptied, positions and FUSION
  slots set to no pattern (heard the same, and no song's order shifts under its jumps), and each run of silent notes
  made one note off. A silent note does more than a note off (it sends MIDI OUT, fires the FILTER, ends the tail
  before it), so this is an edit, not a no-op: it comes unticked, and leaves the runs it cannot clear safely (in
  patterns with jumps or loops, entered past their first row, shared with FUSION, or reaching the pattern's end).
- **A built-in cartridge can be deleted,** on the FM-1 and on the page, as any cartridge is: a small mark in the user
  area hides it from every list; its number is never reused; FACTORY RESET, a disk uploaded without marks, or the
  page's RESTORE brings it back. A cartridge record under a marked number always wins over the mark, since save
  order tells nothing once compaction has rewritten records.
- On the page's FM-1 panel DELETE follows the FM-1's rule; the TABLE keeps taking with an item what uses it, since
  its items have no numbers to keep naming.

**Checked.** Five reads against the specs and the code of the firmware, the playground and the page before it was
settled. They found a "newer save wins" rule that compaction breaks; a first silent-note rule that made later notes
play the previous instrument; the playground's player already apart from the firmware's on a missing instrument (it
kept the note before sounding); a cleanup said to change nothing heard that did (tails, retriggers, slides, MIDI
OUT); the FM-1's use count reading the patterns alone where the specs say the loops follow too. All are resolved in
the proposal, `specs/proposals/202610311848-editor-instruments.md`.

**Commits:** to be added once committed.

## Independent samples: the design

**Why.** A sample belonged to one sampler cartridge: its audio was numbered under the sampler, and an instrument
could play only a sample of its own cartridge. One sound used by instruments in two samplers had to be copied, a
sampler's CLONE or MOVE copied its audio in the flash at once, and the EDITOR page could not make an instrument in
one sampler from a sample another one held.

**How.**
- **A sample is a record of its own,** of a new kind, numbered `00`-`FF`, carrying its entry (length, rate, coding,
  name) and its audio unchanged. Any sampler's instrument names any sample by its number. A sampler cartridge holds
  instruments only, and its CLONE, MOVE and DELETE are those of any cartridge.
- **A new kind, not a new version of the old audio:** the old key named the sampler and a place in it, the new one
  names the sample alone. As separate kinds the two never share a key, so old and new lie side by side while a
  conversion runs. To the store both kinds are audio (records that cross blocks, blocks never compacted): a firmware
  that stopped treating the old kind as audio would take it for damage and free its blocks before it could be
  converted. Only playing the old audio stops.
- **Deleting a sample deletes the instruments that use it,** in every sampler, after its warning; deleting an
  instrument never deletes its sample, and CLEAN UP removes the samples nothing names. When storage is full the
  sample's deletion is saved first and the samplers after it, so a cut between leaves silent instruments naming a
  missing sample, grey and listed. A REVERT that brings back an instrument takes its sample's pending deletion back
  with it.
- **On the FM-1** THE SAMPLES list holds every sample. It opens from a sample instrument's SAMPLE, from REPLACE
  SAMPLE and CREATE in a sampler's menu, and from a line at the end of the cartridge list; K1 turns through all the
  samples. A sample deleted in edit mode leaves edit mode first, so HOME cannot silently take the deletion back.
- **On the EDITOR page** a sample is an item on both panels. A sampler moved between panels takes the samples its
  instruments name, each its old number when free, passing over numbers references still name; WRITE to an older
  PT/FM converts down.
- **The old form is converted by the pages:** the EDITOR page as it loads anything, and the install page after an
  install, by itself, as the files' rules always said. It converts whole samplers a save, in number order, into free
  blocks only, everything else on the FM-1 left unread and untouched, so a cut at any moment leaves the samplers
  converted so far and the rest as they were, and the next install goes on. Two samples merge only when their whole
  records are equal (the same audio under two names stays two, so no name is lost). A sampler too big for the free
  room, or for the store's list of records, stops it with a way out (delete something, or the EDITOR page's WRITE
  after its backup). The demo disk is numbered as the conversion numbers it.
- **Going back to an older PT/FM needs a copy first** (READ, then DOWNLOAD DISK): its store takes the new samples
  for damage and frees their blocks.

**Checked.** Three reads against the specs and the code of the store, the uploader, the install page and the UI
before it was settled. They found the first conversion plan writing over the old audio with no copy whenever the new
samples did not fit beside it, which is the usual case; the old and new keys meeting; the store's audio rule tied to
the old kind, so the new firmware would have freed the audio it was about to convert; going back losing samples; a
sample deleted in edit mode undone by HOME (so already); the store's list of records filling during a conversion;
and gaps in the FM-1's screens and help. All are resolved in the proposal,
`specs/proposals/202611021310-independent-samples.md`.

**Commits:** to be added once committed.

## FX after DJ played and stopped

**Why.** Once DJ's decks have played, they stay what is held after they stop, as a song does: the keys play through
DJ's FX setup. But FX opened outside DJ edited the current song's setup then, so what was changed was not what was
heard. The loops had had the same mismatch and were given the rule that FX follows what the keys hear.

**How.** DJ follows the same rule: with the decks playing or played and stopped, FX from any screen edits DJ's setup,
titled `DJ`, until a song, a pattern or the loops start or UNLOAD SONG lets the decks go (`specs/ui/screens/fx.md`,
`dj.md`). The playground already worked so (its setup follows what is held); the firmware picked DJ only while the
decks played, and now picks it while they are held.

**Tested** on the PC: the same steps in both twins (the decks played, paused from PLAYBACK, FX there: DJ's setup,
GLO's title `DJ`; then UNLOAD SONG), in the firmware's UI tests and the playground's. Not yet on the FM-1.

## STATUS' figures from measurements

**Why.** STATUS PERFORMANCE's EFFECTS was drawn as a constant `0.0%` though the spec says it is measured, and the
shares given each engine's voice (DX7 5.6, JUNO 4.4, TB-303 2.8, SAMPLE 1.6 %) had no recorded source: they came
from the screen's first mockup. The FX screen's footer showed estimates for each effect the same way.

**How.** EFFECTS is measured as the spec says: one pair of timer reads around the whole effects stage of each audio
block, on whichever core runs it (DJ's mix of the decks on core 1, the block's effects on core 2 or core 1, the four
blocks together when the effects take them so), kept with the block and added up by core 1 at the next half's start,
once core 2 has finished the half; the screen asks every tenth of a second, and each ask keeps the measuring on for
about 0.2 s, so nothing is timed once STATUS is left. The shares are now the FM-1's own figures, from the autotests'
live runs (the KEYS scenarios at 4 voices held, every block paying its cache misses): DX7 3.9 %, JUNO 3.4 % (the
mean of a resonant patch's 3.9 and a plain one's 2.9), TB-303 3.3 %, SAMPLE 1.1 %; CHIP keeps 2.5 %, a triangle at
A-4 measured alone, the only figure there is for it. The effects' figures likewise: CHORUS 2.1, DELAY 3.1, REVERB
8.3 and the LIMITER 0.2 % as they work in the demo songs; GATE 1.1, FILTER 1.2, DRIVE 2.2 and LO-FI 1.0 % measured a
block alone (no live figure of their own: the songs' inserts are counted together); DUCK and the METRONOME stay
estimates. The playground uses the same numbers for its CPU estimate, its STATUS and the FX footer, and counts the
punch-ins' buffer (1.5 %, which records what is heard always) in its EFFECTS, as the FM-1's measurement does.
`status.md` gives each figure's source. Set aside: a warm bench's figures (lower, as no cache miss is paid).

**Tested** on the PC: STATUS measures while shown and stops once left (the UI tests); the twins' screens compared.
Not yet on the FM-1: the EFFECTS figure itself.

**The FX footer, after.** The footer's figure was still the table's, though its spec says it is measured on the
device, while the firmware timed every effect in every block for a reader nothing called. Now the FX screen turns the
timing on while it is open (off once left; the debug build's stages time every block as before) and reads the picked
effect's sum every quarter second: its share of the audio's time, the decks' own GATE, FILTER, DRIVE and LO-FI
included on DJ. The first quarter second of a pick names the effect alone; DUCK, whose work is spread through the
tracks' mixing, keeps its estimate; the emulator (its clock stands still inside a half) and the playground keep the
table. Tested on the PC: the suites and both builds; the measuring itself only on the FM-1, not tried there yet.

**Commits:** to be added once committed.

## The EDITOR page's recorder and cutting samples

**Why.** Sounds came only from files: a drum played into a microphone, or what the FM-1 itself plays, had to be
recorded elsewhere first, and a recording of many hits could only be kept whole or cut once by hand.

**How.** The design is the proposal's (`specs/proposals/202610311701-editor-recorder.md`), written into
`specs/editor.md`. The recorder takes the input the browser offers at the input's own rate, its voice processing off,
through an AudioWorklet that hands each chunk to the page (a ScriptProcessorNode where a worklet will not load); a
take is kept whole in memory and saved as a sample at 16 bits and 44.1 kHz, the take its original. The SAMPLE tab
now shows the sample as it is and selects across it, so a trim is a deliberate TRIM rather than a side effect of a
drag. Slices are found from the level in 5 ms windows: a start where the level jumps by SENSITIVITY's step over the
window before, its attack kept by starting 5 ms early; an end where the sound stays under a silence level 40 dB below
the loudest peak for 100 ms. Markers moved by hand find the ends again from the starts. REMOVE joins what is kept from
the original's own frames with 5 ms crossfades, and remembers how each frame moved, so the instruments that play the
sample follow on SAVE (a point inside a removed part lands at its join, a loop left with no length turns off). New
samples are named by one rule (the name's trailing digits read off, then the first free two digits). MAKE A KIT builds
a sampler with an instrument a slice and a FUSION cartridge whose 128-row pattern holds each slice on its own key,
on the FM-1 panel placed as a move from the TABLE places items, so numbers and room are checked the usual way.
Slices and markers are kept in the tab's draft, so the tab's UNDO takes them back, and never stored. The originals
are kept in the browser apart from the panels, each under an id tied to its audio, so a change elsewhere on the page
writes only the panels again; one is dropped when the panels no longer name it, and a take's SAVE writes its
original first, so a browser that cannot keep it refuses the SAVE. The page's own player (a take, a sound the
preview's room cannot hold) plays through the browser at the sound's rate and the footer's VOL, and shows in the
footer as the preview does. After a review: TRIM SILENCE keeps the markers inside the part kept as TRIM does (it
dropped those across its ends, and the slices picked then named others); a slice quiet for less than 100 ms before the
next start ends at that start, as the spec says (REMOVE SILENCE took such gaps out of fast loops); a long take is
joined without spreading every chunk into one call (a take of minutes failed silently); a take's original written by
its SAVE is kept until a state names it, so a save of the state from just before cannot drop it.
After the first look at it: the take's waveform is drawn while it runs (a minimum and maximum kept every 256 frames as
the chunks come, the box 10 s wide until the take is longer, its end a light red line), a white line follows ▶ over
the take (the page's own player tells where it is; the waveform kept as an image under it), RECORD stops ▶, and SAVE
closes the recorder, the status line naming the sample. Then a selection on the take: a drag selects a part (its ends
dragged move them), TRIM SILENCE selects its sound by the SAMPLE tab's rule (the slices' silence level and margins),
WHOLE TAKE clears it; ▶ plays the part and SAVE keeps only it, the part its original, while the take stays whole in
the dialog until then. And one channel at once: a stereo sound (a drop, a take from a stereo input) is mixed as it
comes (`sampleOf` mixes whatever reaches it; the recorder mixes at STOP, its waveform the mix while it runs), so its
original is that mix and every sample on the TABLE goes to the FM-1 as it is; the SAMPLE tab's CHANNELS went with it.
An original stored stereo before is made one channel when the page loads it, as its CHANNELS had it (the mix, or one
side alone), under a new id, the stereo one dropped at the next change kept.

**Tested** on the PC: in Node, the naming rule, TRIM SILENCE, slice detection on a sound of known hits (silent
slices, SENSITIVITY, a flam counted once), slices from starts, the joins and the points carried over them, and the
new samples and kits on both panels (a full sampler, a sampler's open tab, a slice too long, 65 slices); in a
headless Chrome with a fake input, a take recorded, saved, replaced and discarded, played through the footer's
player, its original kept apart and back over a reload, dropped once nothing names it, and the SAMPLE tab's
selection, TRIM with UNDO, SAVE AS A NEW SAMPLE, DETECT SLICES, a marker added, SAVE AS SAMPLES, MAKE A KIT and
REMOVE SILENCE. Left for later: a Worker for the new samples' conversion (a 20-second stereo take at 48 kHz converts
in about 0.6 s on the page's own thread, the page waiting that long).

**`TOO LONG`, after.** A sample's length is 20 bits, so a take longer than about 23.8 s could not be saved at all: the
recorder refused it with no way to cut it there, though recording long and keeping only the pieces that fit is what
the recorder is for. A loose sample on the TABLE may now be longer than a sample can be: a take, a dropped sound
(refused before) or a piece cut from one. It holds its original and its cut, and no record; its size reads `TOO LONG`,
its picture comes from its original, it plays through the footer's player, its tab says how long it is and what
makes it fit, and a move to the FM-1 panel is refused with its length. TRIM, REMOVE, a lower RATE or OPTIMIZE (a
level that makes it fit counting as smaller) turn it back into a sample; WHOLE SAMPLE or a higher RATE make a loose
one long again. A part too long for a sample is known before any work, so a long sound is not converted only to be
refused. Kept in the browser as any sample with an original; one whose original the browser lost goes with it.
**Tested** on the PC: in Node, a take, a drop and new samples kept `TOO LONG`, refused by moves (alone, with others,
onto a sampler) and by MAKE A KIT, TRIM, a lower RATE and OPTIMIZE making it fit, WHOLE SAMPLE making it long again,
its hash its original's, a lost original; in the headless Chrome, its row and bar, ▶ through the page's own player,
the move refused, its tab, TRIM and SAVE making it fit and the move taken, a reload.

## The EDITOR page's instruments, many at once

**Why.** A cartridge tab picked one instrument at a time, listed slots only up to the last used, and moved nothing:
putting a bank in order, or bringing instruments from one cartridge into another, meant doing it on the FM-1 one
slot at a time.

## FAVORITES: built

**Why.** The design above, made: the firmware and the playground, as the specs written from it say
(`specs/files/instruments.md#favorites`, `specs/ui/screens/instruments.md#favorites` and the others it names).

**How.**
- **The record and the store.** Kind 0x07 is the last cartridge kind, so wherever the kinds are read in turn another kind
  under the same number is found first; its slots are pieces of 3 bytes, an empty one marked by its slot byte `FF`. At a
  mount (and after REVERT ALL) a FAVORITES record sharing its number with another cartridge kind is left out by an edit,
  so the next SAVE writes its deletion. The built-in `FB` is one record more among the built-in instruments (the packer
  makes it), so the EDITOR page's build sees it as the firmware has it. The reader of a cartridge's instruments never
  returns a favourite: nothing takes `FB:07` as an instrument, so a cell or loop naming a FAVORITES cartridge's number
  plays nothing, and the pipette and the EDITOR's instrument knob pass it by, without a line of their own.
- **The place and the instrument.** The current instrument stays what everything plays, records and saves; a second
  value, the current place, is where the cursor stands and what PRESETS, SEL + PRESETS, MIDI's program change and bank
  select turn from. Picking a place sets both; a favourite gives its source, an empty or missing one leaves the
  instrument as it was; a change to the favourite at the cursor (an edit, a REVERT, a rewrite) is followed when the
  store's generation moves. Every use of the old single value was read and put on one side or the other.
- **One order for the lists.** The cartridge lists take their numbers from one function, and one reordering puts FB
  first and the user's FAVORITES next; the floating cartridge of a MOVE is sorted by the same rank. The playground keeps
  its cartridges in that order.
- **INSTRUMENTS.** A FAVORITES cartridge's slots show their sources; the details below are the source's, drawn by the
  instrument's own code with the source standing in for the cursor's place. A favourite's edit mode writes each pick
  into the slot at once under the edit mode's copy, so HOME drops it as every edit mode does; K1's cartridge list is the
  shared one, closing a second after the last click. ADD TO FAVORITES reads the target's slots once and adds all or
  nothing. NEW CARTRIDGE and the cartridge list's NEW share one maker.
- **The references.** The favourites are counted in the uses the questions show and rewritten with the cells by a
  MOVE or SWAP answered YES; a DELETE's rewrite passes them by. CLEAN UP counts them as uses and never lists a FAVORITES
  cartridge; AUTO LEVEL ALL leaves them out; CHECK REFERENCES lists a missing one.
- **SEL + GLO** is checked at GLO's press with SEL down, before any other combination, using SEL's combination lock;
  it remembers the place before a FAVORITES cartridge became current and the favourite last stood on.
- **GLO + PRESETS** is checked before PRESETS' own work, with GLO down and its combination not closed by another
  control (GLO's lock taken at the first click); it sets the instrument alone (the instrument's half of ui_set_inst, split
  out) and marks it as picked once, so the follow-up that keeps a favourite place's source current leaves it be until
  the place changes. Its list is PRESETS' instrument list drawn for the FAVORITES cartridge, with no timeout, closed at
  GLO's let-go. The cartridge walk is shared with PRESETS' (step_from).
- **The room.** The debug build had about 2 KB left, and this needed about 5 KB. The linker now leaves out what nothing
  reaches (`--gc-sections`, the linker script's KEEPs as the roots), which freed 3.6 KB of functions no build used and
  changes nothing that runs. After FAVORITES: the release image 574,276 B (7,288 B left), the debug image 580,564 B
  (1,000 B left).
- **After a review of it.** SEL + PRESETS (and MIDI's bank select) in either edit mode could land the edit on a
  cartridge of the other sort: a favourite's edit then wrote its 3 bytes as a whole instrument's (read past its
  buffer), an instrument's offered INIT and RENAME on a favourite. In edit mode they now turn only the cartridges of
  the edit's own sort. A cartridge MOVE with the cursor on a favourite now takes the current instrument along when it
  lies in the moved cartridge, as the playground did. ADD TO FAVORITES lists the first six FAVORITES cartridges, the
  menu's room, in both twins (the spec says so). The EDITOR page's DELETE of a FAVORITES cartridge with ALSO WHAT ONLY
  IT USES took the cartridges only it named; it leaves them now.

**Tested** on the PC: the store's tests (the record's pieces, an empty favourite as none, FB changed and emptied, a
DX7 cartridge written over a FAVORITES record by an older firmware winning at the mount and the deletion saved), the
seeding's (the kind accepted, FB among the built-ins); the firmware's UI tests (ADD TO FAVORITES and its three toasts,
marked slots, SEL + GLO there and back (with SEL's hold layer showing too, GLO lit dim), NO FAVORITES YET and refused in edit mode, GLO + PRESETS (refused on INSTRUMENTS; a favourite once, the place kept, its list while GLO is held, GLO's tap not done, PRESETS alone on from the place, SEL + GLO sharing the favourite last used, GLO's layer and its let-go), PRESETS skipping empty and missing
favourites, the instrument kept on them, a favourite's edit mode with K1, PRESETS, HOME and EDIT, an empty one started

## Safe installs: the start check, PT/FM's update loader, the debug part

**Why.** An install cut short (a cable pulled, the power lost) left the FM-1 dark: the chip's boot code looks for the
request to run the update loader in RAM only, so it never resumed, and the USB rescue lived inside the firmware being
overwritten (from the first block written until nearly the last, new code ran into old). Past that, only outside
tools on the chip's own USB mode brought it back. The FM-1 showed nothing while installing either.

**How.**
- **The start check** (`fw/stub`): the slot's first code, 2,872 B in the 3,808 between the directory and 0x5000; the
  firmware links from 0x02001000. At every start it scans for OCT- (48 ms), reads the firmware's request (a box of
  16 B at the top of the RAM records), checks the mark (the slot's last 32 B: the body's length and CRC-32, its own
  CRC-32) and the body's CRC-32 in place; all good, the firmware; else the update loader kept in the staging, once;
  else the chip's own USB mode. It reads the staging's head with a direct read from a RAM routine (the flash driver's
  read alone: `FL_READ_ONLY`), so it touches nothing of the firmware's.
- **Its bytes never change between builds,** so an install never rewrites the slot's first block: the mark's last 2
  bytes make app.bin's CRC16 0x5054 in every build, which keeps the directory's CRCs there constant (the CRC is linear,
  the lengths fixed). `stub.lock` pins the start check's bytes and the packaged first block; a change takes
  `--renew-stub`, as it costs one install with nothing to fall back on (~44 ms).
- **PT/FM's update loader** ("ota-FM-1_901", 9.6 KB staged, from the one before): it fetches the mark's block first
  and erases it when it is another build's, writes everything else, and writes the mark's block only after the whole
  package's CRC checks out; it writes the slot alone (the old scan that could erase user-area blocks ending in a
  record-like pattern is down to the staging's last block). With PT/FM's pages it asks each block's CRC-32 first and
  fetches only those that differ (F0 22 24 35 7C F7 starts it so; other installers keep the old way). Its screen is
  its own: the panel set up, an 8x16 font of the 43 characters it draws, a bar of the slot's 143 blocks.
- **The firmware** keeps a loader of its own in the staging (both marks in its first bytes), erases anything else,
  and no longer writes the update record's flash copy, which nothing read. The USB RESCUE screen went: two failed
  starts set the box's request and restart into the start check.
- **The debug part:** the debug build was 3,100 B over once the slot lost 3,840 B to the start check and the mark. Its
  cold code (FIGURES and RECORDS put together, the layout's proofs and their texts, FREEZE's frame count, the stack
  painting, the pass timing) is marked `PLAT_DBG` and linked at 0x020F3020 (flash 0x0F7020), extracted apart with a
  head (its build's CRC-32, length, CRC-32), and written by the debug page through seeding's blocks into a region the
  debug build reports and never plans into; its user area ends at 0x0F7000. Every call into it waits for the head to
  check out (at the start, after every seeding), and a crash inside it leaves it off; the PC limit reaches its end.
  It holds 3,512 B; the debug image keeps 212 B of the slot, the release 3,176 B.
- **Set aside:** keeping the old loader byte for byte with a CRC check alone (the mark would stay valid during a
  write: the start check would rely on the CRC alone); the loader kept inside the slot (an install that brings a new
  loader would rewrite the copy it needs); cutting debug features instead of the debug part.

**Tested** on the PC: the start check's decisions, the loader head it takes, its update record against the
firmware's, a built slot's mark and a damaged byte in any block refused (`stub_test`); the loader with and without
hashes, from the release before and between builds, the mark's block first and last, the slot's first block left
alone, a damaged byte, a damaged package leaving no mark, no "success", another flash chip, and a power cut after each
of ~2,400 erases and pages (about 400 cut points): never a mark over a body not its own, and a new session finishing
each (`ldr_test`); the firmware's step 1 keeping PT/FM's loader and erasing another (`ota_test`); the loader's
screens drawn and looked at (`ldr_screen_test`); the install page against a simulated FM-1; the whole firmware suite.
Not yet on the FM-1.

**On the FM-1** (the first runs): the loader's screen showed CHECKING and WRITING; a power cut during WRITING came
back in UPDATE MODE and the install finished, skipping what was written (so the boot code needs nothing of the
mark's block); OCT- at power-on gave UPDATE MODE; RECORDS read the start check's CRC-32 of the firmware at 26.5 ms.
Two bugs it found, both fixed: a small helper of the audio interrupt's and the flash reads' had been moved into the
debug part, so they called into it unguarded (PT/FM CRASH at every start once the part was gone: the build now
refuses any call into the part but from its guarded callers); and the debug page's rewrite of the part erased it
while the firmware still ran it (nothing calls into it now from a seeding's BEGIN to its end). RECORDS also showed
the start check's box counting on through a switch-off: RAM outlasts a short power-off, so the start check takes a
power-on from the chip's reset reasons, as the boot guard does. That change of the start check also lets it find a
loader at the flash's end (0x0FC000, a bigger one from 0x0FA000) before today's staging, so the staging's move
needs no other change of it: one more install with the first block written, then none.

**Left:** the staging moved to the flash's end (12 KB kept for PT/FM's loader, a bigger one staged over the user
area's last 8 KB, the user area one region of 420 KB, with a move at the first start); the install page saying when
the FM-1 has no loader kept.

## Room in the slot

**Why.** LOOPS is to be rewritten with new mechanics, and the slot had no room for it: the debug build had 216 B
left, the release 3,144 B. LOOPS itself takes about 46 KB of the image today (its screen, its records, RECORD LIVE's
song, the pattern recorder and the player's lanes). The search looked at what the image holds, object by object and
function by function, for bytes that do nothing for the sound or the screens.

**How.** Eleven changes, each measured in a real build and kept only if nothing it does changes:

- **Fonts** (9.1 KB): the device's own screens (the crash, the update, PT/FM STOPPED) carried an 8x16 font of their
  own at 4 bits a pixel, every pixel either off or full; they now draw from the app's own font rows, a bit a pixel.
  The app's 8- and 6-pixel fonts keep a byte a row instead of 16 bits.
- **Three sound files built for size** (5.1 KB): DJ's, RECORD LIVE's and LOOPS' records' code runs in the main
  loop, but for LOOPS' hooks at a song's or a pattern's start, which run seldom; built whole for size instead of
  speed.
- **Tables nothing reads left out** (3.8 KB): each table now has a section of its own, so the link drops an unused
  one as it drops an unused function (the device's 6x12 font, used only by code nothing calls). The update loader's
  and the start check's bytes are pinned, so this applies to the app only.
- **State kept out of the image** (3.5 KB): a screen's state with a few initialised fields went into the image
  whole, its buffers included; the buffers are now apart, zeroed at the start.
- **The texts packed tighter** (3.7 KB): a token is as many bits as the table needs (10 now, was 12), every table
  size is tried, the index keeps a byte a text and every 16th start, and each text is spelled with the fewest
  tokens of the table. Packing takes a few seconds, so the build keeps its result while the texts stay the same
  ([texts.md](../ui/texts.md#compression-a-tokenizer)).
- **Main-loop code in the sound's files built for size** (4.2 KB): the request posting, which had been copied into
  each of 66 request functions, 16 more functions the interrupts never reach, and the effects' event (a punch, a
  click, a kill), copied into its seven callers: one copy each, called.
- **USB audio's resampler table** (2.0 KB): its rows mirror each other, so the image keeps half and the start fills
  in the rest.
- **One copy of a table core 2 reads** (256 B of the image, 512 B of core 2's room).

**Measured** (the device compiler's builds): the release image 542,884 B, 34,840 B left (31.7 KB more); the debug
image 545,844 B, 31,880 B left; RAM 64 B better; core 2's room 1,628 B left in the release; the interrupts' stack's
worst case 6,836 B. With these, LOOPS takes about 41.2 KB. A whole build is faster too (about 15 s from nothing,
10 s with the texts unchanged, from 19 s).

**Tested** on the PC: the 18 demo songs rendered with and without the changes, the same sample for sample, and USB
audio's packets the same; every UI test's screens the same, pixel for pixel, and the device's own screens' texts;
the whole firmware suite. Not yet on the FM-1.

**Set aside:** the built-in instruments compressed (up to 18 KB, but a song's instruments would have to sit in RAM,
which is not there); Huffman-coded texts (about 770 B, for a slower decoder); code merged where only its parameters
differ (about 500 B: the code is already factored, the largest repeat a dialog's set-up); the device's start-up
code built for size (about 0.8 KB, by splitting its one unit); tables made in RAM at the start (no RAM for them).

**Commits:** to be added once committed.

## LOOPS: the stage, built

**Why.** LOOPS recorded a layer as a take: armed, one pass of the length, kept as played, so a part had to come out
right in one pass, a retake threw the loop's notes away before the new pass was played, and the first loop set the
length a bar at a time. A looper is played the other way: the music goes round and what is good is kept. The design
([the stage proposal](../proposals/202611030330-loops-redesign.md)) was settled with its specs
([ui/screens/loops.md](../ui/screens/loops.md), [files/loops.md](../files/loops.md),
[files/ram.md](../files/ram.md#the-stage-in-the-edit-memory) and the others its section 19 names) and built in the
playground first; this is the firmware following them. The takes, the re-record and the peel are gone with it (the
reviews' leftovers above were fixed in the loop station that came before).

**How.** In the proposal's ten steps, one at a time, each tested on its own, the playground the twin of every
behaviour:
- **The record** (`play/loops.c`, `rec.c`, the EDITOR page's records): the length always set (4 bars, or the most whole
  bars that fit 128 rows) and kept with no loops; VIEW and K1-K4's jobs in the head's spare bits, each loop's SHIFT in
  its entry's, so the record stays version 4 and a record from before reads with the defaults. A loop as it is heard
  (its repeats written out, a note off where it rests, the cut at the wrap, turned SHIFT rows) is one piece of code that
  EDIT, LENGTH, SAVE TO PATTERN, QUANTIZE and the cut's question all use: LENGTH writes a shifted loop out first, and
  before a longer length a loop whose last repeat the old length cuts, so the new bars are silence. REC's write takes
  the stage's stream as it was heard: MONO merged as it played, the stray note offs OVERWRITE leaves dropped, the notes
  EDIT brought as they are. QUANTIZE works in whole ticks (the playground's floats rounded some halves down: fixed
  there). The EDITOR page's WRITE to an FM-1 that reads only version 3 writes each loop out as heard and names VIEW,
  K1-K4's jobs and the length as not kept.
- **The stage's piece** (`store/store.c`): the stage's notes are a piece of the edit memory under a key of their own,
  above every record's and every edit mode's copy, so no edit counts, saves or reverts them and an edit mode's start or
  end passes them by. A save's end and REVERT ALL drop every entry below the stage's and leave it where it lies, the
  room under it free until the next squeeze moves it down; nothing is copied. The pieces' top piece now grows where it
  lies (the stage grows a note at a time). The player is told of its changes as of a loop's stream; a change is refused
  whole when the edit memory is full, past 3,800 B, or while the store is busy.
- **The player** (`play/player.c`): the stage is one loop more in its view of the loops, read from the piece, played
  once over the length on four lanes of its own, the keys on it on four more. A key's note asked for at its landing row
  stands in for the stage's cell there that once, so it is heard once as played and from the stage after. The lanes a
  key down (or OVERWRITE) replaces are not read from their row; the loop the stage stands for is silent; MONO plays a
  POLY stage on one voice, merged from its first row as REC writes it. The stage's voices carry a mark in a byte of the
  voice that was padding and the mute check passes them by, so every per-track part of the mix (LEVEL, PAN, the sends,
  DUCK, the filter's envelope) is the loop's by construction; a seventeenth track with its own channel state was set
  aside for its RAM and the lines walked each block. Each loop is read at its SHIFT; a jump moves the replay's next row;
  the loops' clock runs with no loops; the take and the first loop's clock are gone. The pattern recorder's preview
  plays a step a row with its ties and NOTE LENGTH, and REC hands the sounding notes on without a break (the preview's
  to the stage, the stage's to the loop written). RECORD LIVE's song takes what the player plays, each loop at its SHIFT.
- **The screen** (`ui/scr_loops.c`, written anew): the stage built again row by row into its piece at each change (a
  note's start checked first, a refusal shown in the header with nothing changed), a held key's span growing with the
  line each pass of the main loop, OVERWRITE's eraser, REC's jobs in the spec's order and its half second of rest after
  each, EDIT, the arm, PLAY and the play position (a jump while playing), K1-K4's jobs, VIEW, the twelve properties,
  ADJUST, the SEL menu, and the new drawing: four slots, the overview column, the stage's panel, the length's bar, the
  hint line. A button's press now reaches the screen itself, as LFO's OVERWRITE acts at its press; the header's `BETA`
  went; the properties dialog takes twelve items and draws their names as it goes (200 B of RAM back).
- **The pattern recorder** (`ui/lp_rec.c`, written anew): each row's steps and ties as two masks, a tap at its
  release and a hold a tie (no tie ever left alone), K1 NOTE LENGTH, K2 LENGTH, K3 the note; its REC puts the pattern
  onto the stage. Its step keys' holds share CONTROL mode's state (the recorder takes the keys while open). What plays
  on into LOOPS pauses as it opens, as the preview alone runs on the loops' replay (the playground follows).
- **The help and texts:** LOOPS' help pages are the spec's; the texts' build now checks where each key's reading comes
  (ENV's and SEQ's at their first mention, ARP's once and again only where ARP holds something on, LFO's at most once;
  ARP's reading in the help and the manual is AUTOMATIC REPEAT PROCEDURE),
  and the playground's check holds the same rule. None of the loop station's texts is left.
- **The state and the AUTOTEST:** the state ends with LOOPS' 4 bytes (335 B, still version 1: a reader takes a shorter
  answer as older), given on every screen; the debug build's seven LOOPS scenarios play the stage, each REC at least
  550 ms after the last. Their TB-303 scenario found the keys of a chord pressed with the arming key played freely
  instead of landing on the stage; they land with it now, as the spec says.
- **The EDITOR page:** the LOOPS tab shows the length and edits each loop's SHIFT, signed the nearer way round.
- **The manual:** the LOOPS chapter, appendix B's LOOPS messages and the chapters that quote LOOPS follow the stage;
  every LOOPS picture made again from the new screens, four new (a loop on the stage, OVERWRITE, ADJUST, a tie).

Settled with the specs on the way, in both twins: for half a second after REC does a job it does nothing (a double tap
does one job); OVERWRITE rests in ADJUST and the pattern
recorder; a POLY stage switched to MONO while chords sound ends its other notes at its next row; a jump while a song
records is heard, so the song takes the loops from where they land; a cut repeat ends at the loop's
own row 0 in the first pass too; the play position is taken round a new length.

**Measured** (the device compiler's builds): the release image 558,836 B, 18,888 B left after the stage (35,112 on
the tree it began from: 16,224 B more; the samples' work, below, counts that tree 32 B lower);

## The firmware's room

**Why.** LOOPS' stage took about 16 KB of the slot's room (35.1 KB left before it, 18.9 KB after it, 18.7 KB once the store fix and PLAYBACK came), and the features to
come need room too. The code it added, and the code around it, were looked through for what could be smaller while
doing exactly what it does.

**How.** Nine changes in five groups, each measured in a release build, none changing what the firmware does:
- **A menu item's group count and a text run's colour a word** (2.3 KB): each was a byte at the end of its struct, so a
  menu item or a run written whole made the compiler copy the struct's three bytes of padding with a call, 116 such
  calls in the image. As a word the structs keep their sizes (16 and 8 bytes) and are copied by words.
- **LOOPS' lanes' helpers built for size** (1.2 KB): the sound's files are built for speed, and the lanes' small helpers
  (a lane's voices' track and mark, a voice of a lane's note, a glide's tick, a note, a cell, the stage's lanes held) were
  copied, unrolled, into each of their seldom-run callers. They run per note, tick or row, never per block, so each is
  now one copy, built for size and called, as the file's other seldom-run code is.
- **The stage's reading and the pattern recorder's note offs written once** (0.5 KB): the player and LOOPS' screen had a
  copy each of how the stage's rows are read and a MONO stage merged, and the pattern recorder and its preview a copy
  each of the note offs NOTE LENGTH and the ties make; one copy of each now, in the records' reader all of them link.
- **State kept out of the image** (0.5 KB): LOOPS' screen's state and the player's stage state had initialisers, which put
  them into the image whole; they are set at the start instead.
- **Smaller repeats on LOOPS' screen** (0.2 KB): the instrument's name or EMPTY in one helper, adding a command to a cell
  shared with the loops' records, the stage's cut finding the lanes still sounding with the loops' own function.

Set aside, each needing a design or touching many files for a few bytes: a copy function for texts instead of a format
of one string (about 200 B over 19 files), LOOPS' hint line as a table (150-200 B), 32-bit sums for RECORD LIVE's time
and the MEMORY line (about 60 B), and smaller ones (about 90 B).

**Measured** (the device compiler's builds): the release image 559,012 B before, 554,448 B after, so 23,276 B left
(18,712 before: 4,564 B more); the debug build 20,364 B left (15,944 before); the variables 12 B more in the release,
28 in the debug build (the linker's alignment of the state now set at the start), 8,624 B past the spare zone's own in the
release (8,640 before), 7,968 in the debug build (8,000 before); the interrupts' stack's worst case 8 B less in the
release, the same in the debug build; the UI's variables unchanged.

**Tested** on the PC: the whole firmware suite and the editor's tests; the tree before and after side by side: LOOPS'
lane tests' sessions (several loops, repeats, SHIFT, MONO and POLY stages, the stage's held lanes, jumps, the pattern
recorder's preview, the keys' lanes), every block of their sound the same, sample for sample; DJ's stand the same; the
18 demo songs the same; the UI tests' whole script (LOOPS' stage, the pattern recorder, RECORD LIVE, DJ and the rest)
run on both, the sound it made and every screen the same, pixel for pixel.

**Not yet:** on the FM-1, and what the lanes' helpers built for size cost in cycles there (the PC builds them as before,
so it cannot see it); a note's work per lane is a call more, against fewer cache lines walked.

## The EDITOR page: a disk of the TABLE's selection, built-ins copied

**Why.** The TABLE could only hand its items to the FM-1 panel; to pass a song on as a file, everything had to go
through that panel and its DOWNLOAD DISK, which saves the whole panel. And a built-in cartridge could not leave the FM-1
panel at all, so there was no way to take one as a starting point for a cartridge of one's own.

**How.** DOWNLOAD AS DISK sits in the TABLE's selection bar and is the move itself: the picked items go, in memory, to an
empty FM-1 panel (no records, the firmware's built-ins and defaults, the user area's own layout), and the disk is what
that panel then holds. So it takes what a move takes (a song its patterns and cartridges, a sampler the samples its
instruments name, a FUSION its patterns, a FAVORITES cartridge the cartridges it names), leaves the built-ins out
(references to them stay), takes a changed built-in a song uses at its number, numbers each item as the move does, and
refuses what the move refuses with the same words, `NO DISK SAVED` in place of `NOTHING MOVED`; what would not fit an
empty FM-1 is refused too, a disk being meant for one. Neither panel changes and no step of UNDO is made. The file is
named after the item when one is picked, else after the selection and the day; DOWNLOAD DISK and it now save through
one helper.

A built-in cartridge picked on the FM-1 panel and moved to the TABLE (the arrow or a drag) is copied as a cartridge of
its own: its contents, its changes when changed, its name, and no number to remember, so moved back it takes a free
number beside the built-in; its hash is its content's, so moving it twice makes one copy. What uses a built-in moves as
before: a reference to the firmware's own stays one, and a changed built-in a song takes along still remembers its
number. For that to hold beside the copies, when a move looks for what the other side already holds, a cartridge that
remembers a built-in's number and a plain one of the same content are never the same item, nor are what uses the one
and what uses the other (their references compared in turn); a changed built-in whose number holds another change
still finds the plain cartridge it took a free number as before, with what uses it. The content hashes stay as they
were. Set aside: carrying the built-in's number in the hash of what uses a changed built-in, simpler, but then a song
whose changed built-in had taken a free number was copied again at every later move.

**Tested** on the PC: the editor's Node tests (the copy from the firmware's own and from a changed one, moved twice,
moved back beside the built-in, a song and its changed built-in picked together, a backup keeping a changed built-in's
number, a song's changed built-in landing on its number on a panel holding only its copy, a TABLE song pointing at the
copy naming the copy's number, a pattern whose changed built-in took a free number moved twice and found there the
second time; the selection's disk against the move to an empty panel record for record, put back by

## LOOPS: the stage switched off

**Why.** On LOOPS every note the keys play while the loops go round lands on the stage, and the stage takes the
selected loop's place. To play along with the loops without keeping anything (to find a line before recording it, to
jam over a finished set) the keys needed a way off the stage: ARP's tap switches it off and on
([proposals/202611041720-loops-stage-switch.md](../proposals/202611041720-loops-stage-switch.md),
[ui/screens/loops.md](../ui/screens/loops.md#the-stage)). The pattern recorder, which ARP's tap opened, is now ARP held +
REC, with SEL's RECORD PATTERN as its tap route.

**How.**
- **The switch is a byte of LOOPS' screen's state,** 0 at every start and never saved. Off, the screen tells the player
  the stage's rest: the stage is not read, its notes end, no
  loop is silent, and on again it is heard from the next row. So the stage's silence needed nothing new in the player's
  rows or blocks.
- **The keys with the stage off** sound through 16 lanes of their own, after the stage's keys' four (the stage's keys'
  lanes 4-19): each note at once, in the keys' instrument, on the stage's column (the mix REC would put the stage in,
  LOOPS' effects, no mute), as the keys on the stage sound, but standing in for no cell and written nowhere. POLY gives
  each key the lowest free lane, as many as the pool's 16 voices can sound, a 17th key held at once taking the lanes in
  turn (a counter from power-on, stepped only by such an overflow: the lane's note is let go to ring out its release, and
  its key, still down, is forgotten); the playground models the same 16 lanes and counter; MONO keeps one lane, with GLIDE's 3xx, LEGATO's LEG or a TB-303's slide as
  MONO LEGATO says. Each of these lanes marks its voices with a mark of its own, so a lane never takes another's voices.
  Set aside: a lane for each of the 27 keys (504 B more, past the release build's spare), and the stage's keys' own four
  lanes (a key held across the switch would cut, or be cut by, the other's notes).
- **ARP forms a combination on LOOPS now:** its tap waits the combination grace on the screen itself; held past the hold
  delay it shows its layer, `REC: RECORD PATTERN`, and let go does nothing. The controls' grammar gained a test for it:
  REC pressed with ARP held, or let go within its grace, on the screen that takes it as its own combination does none of
  REC's jobs at its press, ARP's tap is consumed, and the screen acts at REC's release (LOOPS: the recorder).
- **The rest follows the specs:** REC sends and arms nothing with the stage off (`STAGE OFF: ARP TURNS IT ON`), LFO does
  nothing; EDIT and the recorder's REC turn the stage on;
  switching it off while armed disarms (`CANCELLED`); the title `STAGE OFF` with `REC: STAGE ON` at its right, the strip
  much fainter, the hint line `STAGE OFF: THE KEYS ARE NOT KEPT`, ARP full only with the stage on, REC too; the state's
  byte 334 bit 3, read by the AUTOTEST, which switches the stage on before its LOOPS scenarios and opens the recorder
  with ARP held + REC. The help comes from the specs' pages; the manual's LOOPS chapter has a part of its own for it.

**Measured** (the device compiler's builds): the release image 554,448 B before, 555,800 after (23,276 B left before,
21,924 after); the debug build 20,364 B left before, 19,012 after; the variables 304 B more (the 16 lanes 288 B, the
screen's 16), 8,320 B past the spare zone's own in the release (8,624 before), 7,664 in the debug build (7,968 before);
the screens' variables 28,620 of their 28,672 B (28,604 before); the interrupts' stack as before.

**Tested** on the PC: the firmware's UI test (LOOPS' script as the playground's loops test takes it: the switch after
the grace, the stage dimmed and not heard, the selected loop heard, the keys at once and written nowhere, POLY seven keys,

## RECORD LIVE records what is heard

**Why.** RECORD LIVE wrote a song from the loops' streams, row by row, and to keep that picture true it froze LOOPS while
it recorded: the stage rested, EDIT, the pattern recorder, ADJUST, QUANTIZE, DOUBLE, LENGTH and GRID were refused
(`RECORDING A SONG`), and REC could only end the song. So a performance could not be recorded the way it is played. A
song now records what was heard, whatever LOOPS does: it is another layer before the output, a tap where notes enter
the voices ([proposals/202611042000-record-live-tap.md](../proposals/202611042000-record-live-tap.md),
[ui/screens/loops.md](../ui/screens/loops.md#record-live)).

**How.**
- **The tap is in the player, where a note is given its voices,** and only there: a lane's note as it fires (its row
  and tick need no working out: the replay's tick counter, running on for good, stamps it), a key's, the arpeggiator's, a
  single note of the pattern recorder, and a note losing its voice, taken or parked past the VOICES count. An event is
  10 B in a ring of 64 the main loop reads; there is no work per frame or per block. With the tap off a note pays one test.
- **Only notes that have a voice are written.** A note is told after its voices are given: none (a muted loop, the
  loop the stage stands for, a note past the pool) tells nothing; one losing its voice tells that, and the song gets a
  note off there; a parked note coming back starts nothing, so tells nothing.
- **The song's time is its own:** the loops' replay's ticks from its row 0, over its ticks a row as they were at its
  start. Row and `EDx` come from a note's tick alone, so GRID, LENGTH, DOUBLE or a loop changed or deleted never touch what
  was written. The replay never stops while a song records (PLAY silences the loops, as before), so the count never does.
- **The writer** (`fw/core/play/live.c`, written anew; the playground's twin in `scr-loops.js`) keeps the pattern being
  written as a log of 8-B entries in rows' order, in a borrow of 16,064 B from the spare zone from the arm to the song's
  end, and writes a pattern out as its 128 rows are heard. The log holds 2,000 entries; past them the notes that come are left
  out and counted, the rest dropped.
- **Tracks:** a track holds one source's mix at a time. A note goes on the track its lane held; else on one with that
  mix; else on one unused; else on the free track whose mix differs least, mixer commands on the note bringing it to the
  source's. So loops keep their tracks, and a song's mix follows what was heard; a track takes one note a row, and
  what finds none is heard, left out and counted.
- **What changes is looked for, not told:** TEMPO, the FX setup and the mixes are compared at each main-loop pass with what
  was last seen, and logged as commands at the row heard, so nothing of LOOPS' screen had to know of the song.
- **The keys of a song have no lanes of their own any more.** With the stage on they land on it as anywhere and are
  written as they land, by QUANTIZE; with it off, or while the song keeps the loops silent, they sound through the
  stage-off keys' lanes and are written as played. Their 4 lanes and their queue went, with the stage's rest during a song.
- **REC and HOME:** REC keeps its jobs (armed it still starts the song; playing it sends the stage). HOME tapped ends the
  song, at the row it was pressed in: the row is taken at the press, and the writer holds back the pattern's end until
  the tap comes, or until HOME turns out to be a combination. Armed it cancels. Inside the pattern recorder or a dialog
  HOME is theirs. So HOME tells a tap from a combination, a new call of the controls' layer asks whether a button's tap is
  still to come (it answers from the button's own state, not the clock's, so it cannot be late by a pass).
- **What is otherwise a stop is not one during a song:** LOAD FROM PATTERN leaves the loops silent at their start, and its
  list's PLAY previews nothing, as the song's time runs on.

## A song against SAVE NOW, REVERT ALL and DELETE LOOP

**Why.** Three things a song recording met in the firmware and not in the playground.
- **SAVE NOW** (the answer to `MEMORY FOR EDITS IS FULL`) paused the loops and started the save together. A save under way
  takes no more edits, so the song's end, seen a few passes later, was refused: the rows since its last pattern were gone,
  the whole song if it was under 128 rows, and the last message read `SAVED`. A small save ended before the pause was seen,
  which is how it stayed unseen.
- **REVERT ALL** dropped the edits first, so the song's end came after it: a stray song of the last rows, or
  `MEMORY FOR EDITS IS FULL` with the memory empty.
- **DELETE LOOP and CLEAR LOOPS** told the player the length had changed, which neither does. The replay was built again
  where it stood and the row playing started its ticks over, lasting up to 11 ticks for 6, and every note a song recorded
  after that carried the offset as a note delay.

**How.**
- **A song recording ends first:** a function of LOOPS' screen, called at the start of the save and of REVERT ALL, so every
  save that does not wait for a pause has it, as the playground does. SAVE during playback already wrote the song's last
  pass before it started. With the memory truly full the last pattern may still not fit: the message says so, and those
  rows go, as at any stop by itself.
- **DELETE LOOP and CLEAR LOOPS tell the player the loops changed, not their length.** It reads them again as it does after
  REC, and the row runs on. LENGTH, GRID, DOUBLE, LOOPS' REVERT and LOAD FROM PATTERN, where the length can really change,
  still build the replay again, and their row still starts over; keeping the tick there touches the replay, so it is left.

**Measured** (the device compiler's builds): 32 B. The figures after this and the next section's: the release image
552,200 B, so 25,524 B left; the debug build 22,452 B left; the variables and both stacks' worst cases unchanged. Only
LOOPS' screen and the UI's save and REVERT ALL changed.

**Tested** on the PC: two new checks, a song of 20 rows met by SAVE NOW with a save long enough to be under way, and by
REVERT ALL, each failing before the fix and passing after it; RECORD LIVE's session carried on past DELETE LOOP, whose

## The build's code on the red screens

**Why.** A red screen's numbers are addresses in one firmware image, and a release's version is its number alone: every build of a
version says `0.27`, so a photo of a crash could not tell which build it came from, nor could its addresses be read against the right
image. A report from someone else's FM-1 needs the build named on the screen itself.

**How.**
- **Both red screens** (PT/FM CRASH and PT/FM STOPPED) end with two lines above PRESS A BUTTON TO RESTART: the version, and `BUILD`
  with the build's code. `fw/device/main.c` draws them in the wait both share; the build passes the texts to the device's code.
- **The code** (`fw/tools/buildcode.py`): 8 hex digits for a 32-bit word of the build's time in minutes since 2026-01-01 UTC (24
  bits, to 2057), its kind (release, debug, dev, bring-up) and a 6-bit check, scrambled by a bijection (odd multiplies between
  xor-shifts), so it reads as no date and the tool reads it back exactly. A misread digit fails the check about 63 times in 64.
  `python3 -I fw/tools/buildcode.py CODE` says the kind and the time; the build prints each build's code.
- **The same image again:** a build's time is in its image now, so two builds of the same sources differ. `SOURCE_DATE_EPOCH`, when
  set, is the build's time (the debug build's stamp included), as the manual's build already takes it: the same sources then give the
  same image.
- **Set aside:** a hash of the image (it cannot hold its own hash, and a hash of the sources needs the commit, which a build of
  changes not committed lacks).
- **More of the crash on the screen:** a crash's five numbers could not tell a stack run past its end from a stray pointer, nor
  whether the second core was involved. PT/FM CRASH now names its words and adds what the fault found (`specs/hardware.md`):
  the stack pointer; the write limit hit (`C0_WR_LIMIT_ERR_NUM`, 0x1EEE360: the chip keeps which window, not the address);
  the four branches traced; both stack pointers, PSR and ICFG; the seconds up and the late halves; core 2's state, with its
  own fault's PC when that stopped it. The drawing is its own file (`fw/device/crash_screen.c`), drawn on the PC by
  `fw/tests/crash_screen_test.c` for the widest values, every write limit and every state of core 2, each line checked to

## LOOPS: five changes from play

**Why.** Playing LOOPS on the FM-1 showed five places where it got in the way. A loop REC made came out with no sends,
though the stage had sounded through the keys' own sends while it was played. A pad held from the first row to the
length's end lost its start: at the line the key was written again as pressed at row 0, and its span then erased its own
first-pass note as the line passed it. MONO LEGATO's GLIDE at first surprised more than it helped. A loop's level could be
read only by turning its knob. And after a send (which leaves the stage off) the next take took two presses of REC with
the loops stopped: one to turn the stage on, one to arm.

**How.**
- **The next loop's sends are the KEYS column's.** The next loop's mix as heard is its LEVEL, PAN and DUCK as LOOPS keeps
  them and its CHORUS, DELAY and REVERB SENDS from FX MIXER's KEYS column, one function in the loops' record code feeding
  everything that reads it: the loops' song as the player has it (track `loops_n()`, where the stage on `+ NEW LOOP` and
  the pattern recorder's preview sound), the mix a song recording gives those notes, and the mix REC writes into a new
  loop. The KEYS column reaches the record code as a pointer the UI sets at the start, so the audio context reads the
  values themselves when it reads the song, and a change of them (FX MIXER's column, a send's knob on `+ NEW LOOP`, a
  REVERT or seeding reading the settings again) tells the loops' player as any loops change does, heard from the next
  block. K1-K4 with a send's job on `+ NEW LOOP` turn the KEYS column's value through the setting's own path (unsaved
  until SAVE); LEVEL, PAN and DUCK there stay the next loop's. The record keeps its next loop's six bytes as written: its
  three sends are no longer read, so no file changes. REC into a loop keeps that loop's mix. The tests' constructor of an
  empty loop keeps the stored bytes; no screen makes a loop that way.
- **A key held over the line stops writing there.** At the line its note ends as before (its span to the length's end,
  a note off at row 0 where the lane is free, its sound let go) and the key is forgotten, as a stage-off key whose lane a
  17th key takes: nothing is written for it in the next pass and its release does nothing. The note then plays from the
  stage where it was written, each pass. Keys whose note landed in the next pass are unchanged, and so is every other
  overdub rule.
- **MONO LEGATO JUMP in a new setup:** the default record's byte 2 gets its bit 7; a saved setup keeps its own.
- **Each loop's LEVEL on its slot:** two hex characters in FONT T right-aligned to 226 on the strip's row (y + 14), past
  the strip's end at 208, light grey, dark grey where the loop's notes are (silent, muted, silenced); `+ NEW LOOP` shows
  the next loop's. Nothing else on the screen moves.
- **REC with the stage off records in one tap:** it turns the stage on and, the loops stopped, arms at once as REC arms
  on an empty stage (`STAGE ON: ARMED`), whatever the stage holds; the loops playing, the keys write from there
  (`STAGE ON`). A count-in's cancel and RECORD LIVE's start still come first, ADJUST still refuses it, and REC's 500 ms
  wait follows it as any job. With notes on the stage the arm behaves as any arm with notes on the stage: the next REC
  sends them.
- The specs (the LOOPS screen, FX's MIXER, the loops' record, the controls' table), the help's first LOOPS page (15
  lines, as its header allows), the manual's LOOPS chapter, FX's MIXER and appendix B follow. The controls' table also
  said ARP was lit while the stage is off; it is dim then.

**Measured:** the dev build's image 552,768 -> 552,940 B (24,784 B of FWS left); the variables 58,060 -> 58,064 B (the
next loop's heard mix, a 6-B copy), the spare zone as it was (33,248 B, 8,672 past its own); the worst stacks 7,048 B
(the interrupts') and 4,796 B (core 2's jobs), as before. The 18 demo songs (120 s each) and the session harness (the
keys over songs, DJ's two decks) render bit for bit as before: nothing in their path changed.

**Tested** on the PC, in both twins: the next loop's mix as heard (its sends the KEYS column's, its own kept as written),
a send's knob on `+ NEW LOOP` turning the KEYS column's as a setting, REC writing them into the new loop and keeping a
loop's own on REC into it; in the firmware the stage's note on `+ NEW LOOP` heard with a reverb tail once the KEYS
column's REVERB SEND is turned up while it sounds, and the record code alone with and without a KEYS column; a key held
across the line, POLY and MONO: its note once, a note off at row 0, heard again from the stage at its row, its release
writing nothing; MONO LEGATO JUMP at first and the default head's bytes; the LEVELs drawn where and as they should be

notes on the stage, and playing (nothing armed); the twins' RECORD LIVE session cell for cell; every suite.

## FM-1s with the later flash chip

**Why.** FM-1s made later carry a UCUN UC25HQ80 (JEDEC ID 0xB36014) in place of the Puya P25Q80 (0x856014). The
firmware and its update loader wrote to the flash only when it read the Puya's ID: on the later FM-1s PT/FM's install
was refused (the loader wrote nothing, the old firmware started again), and a PT/FM placed there another way would
have saved nothing and taken no install.

**How.** The two IDs in one place, `fw/hal/fm1_flash_id.h` (`fl_jedec_ok`), read by the firmware at every start and by
the update loader before it writes; any other chip is still refused, so a firmware is never written where it could
not be updated again. The loader's bytes changed, so its pinned SHA-256 in `fw/tools/build.py` with them. A loader an
older PT/FM left staged stays until the next install stages this one (it is told by its marks, not its bytes): it only
ever runs on the Puya. The UC25HQ80's datasheet: the same layout and commands, a program of part of a page leaving the
page's other bytes as they were, no ECC named, nothing against programming a page again in pieces (the store's
appends); a 4 KB erase 7 ms, a page 1.5 ms.

**Measured:** the image 16 B larger (552,940 -> 552,956 B, the dev build).

**Tested** on the PC: `fw/tests/ldr_test.c` judges its simulated chip by `fl_jedec_ok`: an unknown chip (a W25Q80's
ID) refused with nothing written, the UC25HQ80's ID installing the whole firmware; the device suite.

**Not yet:** anything on a UC25HQ80 (the store's appends, the timings, an install).

**Commits:** to be added once committed.

## FX: DRIVE's picture while its knobs turn

**Why.** Turning DRIVE or TONE on FX made the screen lag, as no other effect did. The HARMONICS picture was worked out
anew at every click, on the main loop: 4,510 samples of a sine through DRIVE's law, then 100 samples summed for each of
8 harmonics. `fxm_sin` takes four 64-bit divisions and `fxm_tanh` at least one, all in software on this CPU: about
30,000 divisions a click.

**How.** In `fw/core/ui/fx_pics.c`, what no knob changes is worked out once, at the picture's first draw: the sine of
100 samples, and that sine past DRIVE's low cut, settled (the low cut comes before the clip, so it needs no knob). A
click then drives that one period, settles TONE's lowpass over three periods (0.95^300 left at its slowest) and sums
the harmonics from the sine's table: about 400 divisions. The two tables take 400 B of `.bss`, and the 400 B buffer
they free moves to the stack, so RAM is as it was. The playground's picture is unchanged.

**Measured** on the PC, the old sums against the new over all 10,201 settings of DRIVE and TONE: every harmonic's dB
value, the gain and the cutoff equal, to the bit; the time a click 17 times less, on a CPU whose divisions are in
hardware. With this section's and the last's changes 24,776 B are left in the slot, 21,688 B in the debug build.

**Tested** on the PC: the comparison above; the firmware's and the playground's suites.

## LOOPS: OVERDUB keeps what the stage had

**Why.** A long pad on the stage, another pad overdubbed just before it and held a moment into it: the first pad was
gone, as a held key removed every note starting under it, on all four lanes.

**How.** In OVERDUB (not OVERWRITE, which is as before) a key holds its own lane alone (`scr_loops.c`'s `key_lanes`,
the playground's `lanesOf`), told so to the player (`holds_tell`, `lpStageCut`):
- **its lane:** of the lanes no other key down holds, one free where it lands (nothing sounding or starting there),
  the one whose next cell is furthest; none free, the one whose note ends soonest (`write_note`, `writeNote`). A note
  sounding there is cut where the key lands; a note starting there moves on a row;
- **its span** (`dub_on`, `dubOn`): as the line passes, its lane's rows are cleared and the last note starting in
  them is moved on to the span's end (`lp.push`, `rec.pushed`); a later start or a note's end passed drops the one
  before (covered whole); at the length's end it is gone;
- **let go** (`stage_key_up`, `recKeyUp`): the note moved on is put down where the key ends (let go before the row it
  waits on: moved back to it), and it ends the key's note there; none, a note off as before. The line ends a key as
  before, a note moved on with it gone.

MONO has one lane, never free: the same cut and move. The help's two lines say it: `AND OVER; NOTES ADD UP, NONE
REMOVED`, `(A KEY HELD OVER A START MOVES IT ON)`.

**Tested** on the PC, both twins (`fw/tests/ui3_test.c`, `tests/playground/loops.js`): POLY over two sounding lanes
(the key on lane 2, nothing cut, all notes kept); no lane free (lane 2's note cut, the next start covered whole, the
one after put down where the key is let go, let go a row early: moved back); MONO (the note covered whole gone, the
next at the key's end); a key landing ahead with every lane full (its lane silenced from its landing, the others
heard); the length change, FX and a jump (the key on a free lane, ended where the line was, lane 0 kept).

**Measured:** with the lists' change (above), the image 1,168 B larger: 23,032 B left in the slot, 20,200 B in the
