# Proposal: four more voices on core 2

Status: **settled** (2026-10-22); the specs lead: [../second-core.md](../second-core.md#the-voices-on-core-2),
[../ui/screens/settings.md](../ui/screens/settings.md#voices), [../debug.md](../debug.md). PT/FM played 12 voices at most, all on core 1; core 2 runs the effects and the
output stage ([../second-core.md](../second-core.md)). This proposal lets core 2 render up to 4 more voices, so 16
are heard, and says which voices go there, when, what each core owns, what the flash allows, how parking, SECOND
CORE and the fallbacks work with them, and what the screens show.

## 1. Why

Sixteen voices on core 1 alone overran the FM-1's audio time, so 12 is the most; a song, the loops, both DJ decks and
the keys share those 12. Core 2 is idle most of each half (14-17 % with a song's effects), runs the same engines as
fast as core 1, and can take the voices' render without the voices' mix changing.

## 2. What the FM-1 showed

Measured on the FM-1 ([../hardware.md](../hardware.md)):

- **The engines on core 2 from the flash** run within 0-6 % of core 1 and give the same output sample for sample; the
  code cache is shared, and the same engine code on both cores costs nothing more.
- **12 + 4 fits a half:** 12 voices on core 1 at 48 % of a half at most (all 6-operator DX7s), 4 voices and an
  effects load near a song's on core 2 at 30 %; a hand-over 0.75 µs; core 1 waited ~1.3 µs a half for core 2.
- **Core 2 must not touch the flash while it is busy:** core 2 reading code or data from the flash while core 1's
  erase, program or direct read has the code window off wedges both cores until the watchdog. With core 2 idle in
  RAM around each of core 1's flash operations, voices from the flash on core 2 were right through a 2-minute run of
  ~24,000 operations between them, with no stale line after an erase or a program.
- **The DX7 engine keeps its operators' buses in one scratch for all voices:** two cores rendering a DX7 patch that
  uses them at the same time spoil each other's every block.
- **Core 2's jobs' stack** took 524 B for 4 voices.

## 3. The voices: 12 on core 1, 4 more on core 2

**The pool grows to 20 places:** places 1-12 are core 1's, 13-16 core 2's, and the places past the count hold the
parked notes, as now ([../ui/screens/settings.md](../ui/screens/settings.md#voices)): at VOICES 16 those are places
17-20 (four, as at 12 today), at 12 places 13-20, at 8 places 9-20.

**SETTINGS' VOICES offers 8, 12 and 16, 16 by default.** Up to 12 the voices are core 1's alone, as today; 16 is 12
on core 1 and 4 on core 2. While core 2 does not run (SECOND CORE off, not started yet, stopped by a fallback), 16
counts as 12.

**A new note takes a free place of core 1's first; core 2's places only when all 12 of core 1's sound.** So core 2
renders a voice only past 12 notes at once, and a load that fits 12 runs exactly as today. Then, as now: a free place
anywhere in the count, else one taken from the note least missed, else the note starts parked. A note keeps its place
while it sounds: it never moves from one core to the other, but by parking (below).

**Parking is unchanged:** a held note taken is parked in a place past the count, fading out over 1.45 ms, and comes
back into the first place that frees, of either core, fading in; at a smaller count (VOICES lowered, or core 2
stopping), the held notes in places past it are parked and come back as places free.

## 4. When: a block's voices on both cores

Each block of 64 frames, core 1:

1. makes the block's control as now (the requests' share, the replays' ticks, the notes on and off, the levels and
   pitches, the parked notes back, the Juno-106's noise for the block);
2. when any of core 2's places sounds, hands core 2 the block's **voice job**: the voices in places 13-16, each
   rendered into a block buffer of its own;
3. renders its own voices and mixes them into the block's mix, sends and buses, place by place, as now;
4. waits for core 2's voice job (core 2 runs the block before's effects first, then the 4 voices: together less than
   core 1's 12 at the heaviest, as measured), then mixes core 2's voices from their buffers the same way, in their
   places' order;
5. hands the block's effects and output to core 2, as now.

```
core 1  [control 0][post V0][voices 1-12][mix 13-16][post FX0][control 1][post V1][voices 1-12][mix 13-16] ...
core 2             [V0: voices 13-16]                [FX0 + out 0][V1: voices 13-16]
```

- **Core 2's queue keeps order:** FX(j) is handed over before V(j+1), so core 2 finishes block j's effects, then
  renders block j+1's voices while core 1 renders its own.
- **Core 2 renders only;** everything that needs the tracks, the sends, the mutes, the buses or the screens' figures
  (each voice's gain and pan, the sends, the Juno-106's chorus buses, the scopes, the peaks DUCK and the meters read,
  the end of a voice) stays core 1's, done when it mixes the voice. So the voices' mix, the effects and the output are
  the same code in the same order as on one core.
- **The same sound, sample for sample,** as one core rendering the same 16 voices: each voice renders alone into its
  buffer, and the mix adds them in the places' order. With 12 notes or fewer nothing changes at all.
- **In CUT's halves the voice jobs still go to core 2;** only the effects stay on core 1, as now (its fade decides
  block by block): core 1 waits for the block's voice job, mixes, runs the block's effects and fade, then makes the
  next block. Sixteen voices and the effects on core 1 alone would overrun those halves (16 voices on one core did).
- **The time core 1 waits** for the voice job counts in core 1's share; core 2's job counts in core 2's.

## 5. Who owns what

- **A voice in places 13-16** is core 2's from the hand-over of its block's voice job until core 1 has seen the job
  done: core 2 runs its engine (its state, its block buffer); core 1 touches neither meanwhile. Core 1 makes every
  change to it (a note on, off or cut, a level, a pitch, a parameter command, a park) in the block's control, before
  the hand-over, and reads its buffer and its end after the job.
- **The engines' shared state:**
  - **the DX7's operator buses become one scratch per core** (the engine takes the scratch of the core it runs on), so
    two cores render DX7 voices at once; on one core nothing changes;
  - **the Juno-106's noise** stays one generator, run by core 1 for the block before the voice job is handed over
    (as it is now, before any voice renders); core 2's voices only read it;
  - **the engines' tables** (the DX7's built at power-on in RAM, the Juno-106's and the TB-303's in the image) are
    read only;
  - **the counters** the engines and the voices keep for the figures (the samples decoded, each engine's time) are
    kept apart for core 2, which core 1 adds at a half's start, as core 2's own figures are now.
- **The voices' figures** (VOICES now and its most, STEALS, the scopes) are core 1's, counted when it mixes.

## 6. The flash

**Core 2 may run the engines' code and read voice data from the flash, only inside a voice job.** Its effects and
output job stays in its room in RAM, as now. In exchange, **every operation that switches the flash's code window off
waits until core 2 is idle**, with the interrupts off so no job is handed over meanwhile:

- the store's erases and programs (they wait already, for the halves core 2 writes);
- **every direct read:** the store's, the seeding's, the update's, and the audio context's own path (nothing reaches
  it: below);
- the update's own flash work (its staging's erases and programs);
- the debug build's bench and its PROVE actions that touch the flash.

A wait lasts at most what core 2 was handed: a block's voice job or its effects, a fraction of a millisecond.

**No voice reads the flash by direct reads:** the user area reads in place, and the built-ins are the firmware's
own, read in place too; nothing of the user's is ever in the firmware slot. So no voice, on either core, switches the
code window off while a voice job runs. The audio context's direct-read path stays for safety and waits for core 2 as
every other does.

**The build checks** that every flash operation of the device's code goes through the wait (one entry point each), and
keeps its checks of core 2's room: the effects' code calls nothing outside it; the voice job, in the image, is the
only job that runs code from the flash.

## 7. SECOND CORE, the start, the fallbacks

- **Until core 2 has started** (its first 2 s), **with SECOND CORE off, and after a fallback,** the count is at most
  12: a note in places 13-16 is parked (fading out on core 1, which renders it for that fade) and comes back into
  core 1's places as they free; 16 comes back when core 2 runs again (SECOND CORE on).
- **A fallback during a voice job** (stuck, a misread, a fault): core 1 holds core 2; that block's voices of core 2's
  are not heard (one block, 1.45 ms: their buffers are left out of the mix), then they are parked as above. Core 1
  never renders a block core 2 was handed: it would carry 16 voices and the effects in that block, from a state core 2
  may have left half done. The effects fall back to core 1 as now.
- **No other change** to the start, the holds and the restarts ([../second-core.md](../second-core.md#start-switch-fallback)).

## 8. RAM

- **Four more places:** a voice's state (516 B) and its scope (128 B) each, 2.6 KB, and core 2's four block buffers
  (1 KB): 3.6 KB from the spare zone, which keeps its floor
  ([../files/ram.md](../files/ram.md#the-edit-memory-and-the-spare-zone)).
- **Core 2's room** gains only the voice job's entry, a few hundred bytes at most of the 2 KB left; the engines' code
  stays in the image.
- **Core 2's jobs' stack:** the voice job's deepest (~0.5 KB) and the effects job's (4.8 KB) never nest; the build
  works out both.
- **The cache RAM** ([../hardware.md](../hardware.md#the-cache-ram)) stays in reserve: the four places fit without it.

## 9. Screens

Agreed 2026-10-22. Core 2 is `CPU 2` on the screens, as STATUS names it.

- **SETTINGS' VOICES:** `8`, `12`, `16`; the footer `DEFAULT 16`; the line's text: the notes heard at once, 16 with
  the second core (12 without). SETTINGS' help page: `VOICES: NOTES AT ONCE: 8, 12 OR 16` and under it, indented as
  SYNC PULSE's line is, `  16: 4 OF THEM ON CPU 2`.
- **The toast** at a change: `16 VOICES`, as now `12 VOICES`; when 16 is chosen while core 2 does not run:
  `16 VOICES: 12 WITHOUT CPU 2`.
- **A voice count's colours follow the limit in force:** red at the limit (every voice in use), yellow from 4 under
  it, light grey below: at 12 as now (yellow from 8, red from 12), at 16 yellow from 12 and red from 16, at 8 yellow
  from 4 and red from 8. The same rule everywhere a voice count shows: the header's voices, STATUS's VOICES and MAX,
  PERFORMANCE's VOICES row.
- **The header's voices** (beside the CPU bar) count up to 16, and 17 for the 1.45 ms a note fades out of its place
  at 16; two digits are already drawn in the narrow 3 × 10 font (10 to 99), so only the colours change.
- **STATUS:** VOICES' limit is the one in force (`VOICES 13/16`, or `/12` while core 2 does not run).
- **VISUAL's VOICES:** a tile per voice of the limit in force: at 16, four rows of 52 px (its layout's formula).
- **DJ:** 16 voices as everywhere: its spec's "12 is the most anywhere" becomes the pool's count, whatever SETTINGS
  gives; with both decks full the notes past 12 go to core 2 instead of taking the voices of the deck lower in the
  mix. DJ HEAVY at 16 is measured against its late halves at 12.

## 10. The debug build

- **FIGURES:** core 2's voice jobs' time apart from its effects' (a stage of its own), the blocks with a voice job,
  core 1's waits for them (summed and longest), and the places 13-16 in use (the most).
- **AUTOTEST:** KEYS plays each engine at 1 / 4 / 8 / 12 / 16 voices; DJ HEAVY and a dense song run with VOICES 16;
  38 SECOND CORE off runs them at 12.
- **PROVE** keeps its fallbacks; one more case: a fallback while a voice job is out (the voices parked, the sound
  going on).

## 11. The emulator and the playground

One core, the same sound: the emulator runs the voice job at once where it is handed over (its time core 2's); the
playground's pool grows to 20 places with the same rule (core 1's places first). Both offer VOICES 16, counted as
12 while their simulated second core is off.

## 12. Tests on the PC

- `fw/tests/run_sound.sh`: the voice job run inline and on a second thread against one core rendering the same 16
  voices, sample for sample, for every engine and the parking cases (a note parked from core 2's places, coming back
  into core 1's); the DX7 with its scratch per core rendering on two threads at once.
- The UI tests: VOICES 16, its toasts, STATUS's limit, the playground's pool.

## 13. Not in this step

- **Voices split by cost** between the cores (core 2 taking some of the 12): later, if core 1 runs short.
- **The cache RAM** for the voices or anything else: when RAM runs short.
- **LOOPS' 12 loops:** LOOPS keeps 12 at most (a loop a track, a voice each) until LOOPS itself is reworked; its
  loops simply have 16 voices to share with the keys.

## 14. Expected, to be measured on the FM-1

16 voices without a late half: core 1 about as today with 12 (its own 12, plus the mix of 4 more, ~0.4 ms a half),
core 2 its effects plus 4 voices (~30 % at the heaviest engines). Measured by AUTOTEST (KEYS at 16, DJ HEAVY at 16, a
dense song) with SECOND CORE on and off, and a long run with flash work (saving) while 16 voices play.
