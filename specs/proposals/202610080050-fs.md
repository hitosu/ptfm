# Proposal: files and formats

Status: **settled** (2026-10-08); the specs: [../files/](../files/README.md), which lead from now on
(2026-10-09). Kept as the record.

What PT/FM stores, and how: the store in the flash, and every record in it (patterns and their
commands, songs, the jam, cartridges and instruments, sample audio, settings), how records refer to
each other, how edits reach the flash, and how a data blob gets onto the device. The UI proposal
([202610072229-ui.md](202610072229-ui.md)) says what the screens show and do; this one says what is
kept.

**Words used here:**
- **Record:** one object in the flash: a 16-byte header and its payload. A pattern, a song, a
  cartridge, a sample's audio, the jam, the settings.
- **Kind, number, sub:** what a record is (a pattern), which one (`3C`), and which part of it.
- **Save:** the records one SAVE writes, all with one save number; they count all together or not
  at all.
- **Block:** 4 KB, the flash's erase unit. **Page:** 256 B, the most one program writes.
- **Fast regions:** flash outside the firmware slot, read in place; installs keep them. **The slot:**
  the firmware slot's free part, read with direct reads; every install wipes it.

## 1. The store

A log: records are appended into erased flash, never rewritten in place, and nothing like a directory
is kept. Each save writes only what changed; an old version becomes garbage, and a block is erased
only when nothing in it is still live.

**The flash** is 1 MiB of Puya NOR.
- **Erase** works on 4 KB blocks and sets every bit to 1. **Program** writes 1 to 256 bytes within
  one 256 B page, and only clears bits.
- **A page can be programmed again, in pieces,** before its next erase, also after a power-cycle: no
  ECC over pages or chunks.
- About 100,000 erases a block; reads are unlimited.
- **An erase or a program stops code fetches,** so audio is silenced around them.
- **Measured on the FM-1,** with the interrupts off:

  | Operation | Time |
  |---|---|
  | erase, 4 KB | 17.1 ms |
  | program, 1 to 255 B | 1.93-2.0 ms, whatever the size |
  | program, a full 256 B page | 1.70 ms |
  | direct read | 6 us + 0.72 us a byte (16.1 us for 16 B; 2.95 ms for 4 KB) |
  | read in place, cold | 1.3 us a cache-line fill (0.36 us a 16 B read when sequential) |
  | CRC-32 of 4 KB (table) | 0.2 ms |

  So a write costs its programs and erases, not its bytes: a 4 KB block takes 16 page programs
  (27 ms) and an erase (17 ms).
- **Power, measured on the FM-1:**
  - power-cycles keep everything written;
  - in five power cuts while writing, no record was torn: a program under way seems to finish. A
    torn write stays possible, so every record carries a CRC;
  - an erase can be cut short: the block then reads almost all 0xFF, with a few bytes not (1.5);
  - nothing outside the block being written was ever touched.

### 1.1 Where things go

| Area | Holds |
|---|---|
| 0x000000 - 0x004000 | never: the boot code |
| 0x004000 - the firmware's end | never: the firmware, written by installs |
| the slot after the firmware, up to 0x092000 (~330-530 KB, by the firmware's size) | audio only |
| 0x092000 - 0x093000 | never: the SDK's files, written by installs |
| fast region 1, 0x093000 - 0x0E0000 (308 KB) | records; audio |
| update staging, 0x0E0000 - 0x0E5000 | never |
| fast region 2, 0x0E5000 - 0x0FF000 (104 KB) | records; audio |
| 0x0FF000 - 0x100000 | never: the packages' flash header reserves it for the chip |

- **Records the device writes** (patterns, songs, the jam, cartridges, settings) **live only in the
  fast regions:** an install never touches them, and a power-on reads and checks them in about
  40 ms (1.4).
- **Sample audio** goes into the fast regions first, then the slot. It is placed by the uploader;
  the device never writes audio.
- **Playing from each,** measured on the FM-1 with 16 voices of PTR samples: from the fast regions
  (read in place, as the firmware's own data) 1,059 us of a 5,804 us half; from the slot (direct
  reads) 1,932 us on average, and bursty, up to ~3,600 us.
- **A reserve of 64 KB** (16 blocks) of the fast regions is always left free by the uploader, for the
  device's saves and for compaction.
- **What an install loses:** only audio in the slot, which the uploader writes again.
- **What other firmwares leave** in the fast regions (their settings at 0x0FC000-0x0FEFFF, their
  projects in region 1) holds no record of PT/FM's: those blocks count as free, and are erased when
  the head reaches them (1.5).
- **The update path** marks a pending update with a record in the last 256 B of a block (at
  0x0E4F00, in the staging), where the boot code looks for it. An install's loader erases every
  block from 0x093000 to 0x0FC000 that ends in such a record. A record is told by a marker and a
  CRC-16, so data of the store matches one by chance about once in 4 billion blocks: nothing is done
  about it.

### 1.2 A record

A 16-byte header, then the payload; the next record starts at the next multiple of 4.

| Bytes | Field |
|---|---|
| 0 | kind (0xFF: erased flash, the end of a block's records) |
| 1 | number: which cartridge, pattern, song (00-FF) |
| 2 | sub: a pattern's or the jam's part (0-15); a sample's index in its cartridge (00-3F); else 0 |
| 3 | the kind's format version |
| 4-6 | the payload's length |
| 7 | flags: bit 0 the last record of its save; bit 1 deleted (no payload) |
| 8-11 | save number |
| 12-15 | CRC-32 of bytes 0-11 and the payload |

| Kind | What | Number | Sub |
|---|---|---|---|
| 0x01 | DX7 cartridge | the cartridge, 00-FF | 0 |
| 0x02 | Juno-106 cartridge | the cartridge | 0 |
| 0x03 | TB-303 cartridge | the cartridge | 0 |
| 0x04 | sampler cartridge | the cartridge | 0 |
| 0x05 | FUSION cartridge | the cartridge | 0 |
| 0x10 | sample audio | its cartridge | the sample, 00-3F |
| 0x20 | pattern | 00-FF | the part, 0-15 |
| 0x21 | song | 00-FF | 0 |
| 0x22 | the jam | 00 | the part, 0-15 |
| 0x30 | settings | 00 | 0 |

- **Records the device writes are at most 4 KB** (a 4,080-byte payload) **and never cross a block.**
- **Audio has blocks of its own:** only the uploader writes it, packed one record after another over
  consecutive blocks of one region, and no other record shares those blocks. So compaction never meets
  a block it cannot free.
- **The five cartridge kinds share one number space:** a cartridge number is live in at most one of
  them. Writing a cartridge of another kind under a number deletes the old one in the same save, a
  sampler's audio with it.

### 1.3 Saving

- **One save:** every record a SAVE writes carries the same save number, the next after the highest
  in the flash. The last one has flag bit 0.
- **All or nothing:** at power-on, the records of a save whose last record is missing or fails its CRC
  are ignored. A power cut leaves the state before the save, or after it.
- **Whole pages:** a program costs the same whatever it writes, so a save lays its records out in RAM
  and programs page by page, the flag inside the last record's header rather than as a write of its
  own.

### 1.4 Power-on

- **The scan:** every block's record headers are read, in the fast regions in place and in the slot
  with direct reads; a big audio record's later blocks are skipped. The newest version of each object
  (kind, number, sub) wins; a deleted flag removes it.
- **The check:** the CRC of every record in the fast regions is checked (~30 ms for all 412 KB). Audio
  in the slot is checked by SETTINGS → TOOLS → CHECK STORAGE (~0.5 s).
- **A record that fails its CRC** does not count. As its header may be wrong too, the scan finds the
  next record by trying each following 4-byte step for a header whose record checks: a bad record
  costs only itself.
- **The map:** what is live, and where, stays in RAM: ~12 B an object, ~7 KB for a full store.
- **The scan's worst case,** a header every 16 B over all of the fast regions, takes 8.6 ms (a cold
  header read: 1.3 us in place).

### 1.5 The head, erases and wear

- **The head** is where the next record goes: the erased tail of the open block, then the next free
  block in address order, wrapping around after the last. So the free blocks take their turns evenly
  (wear: section 11).
- **At power-on** the head is after the newest save's last record, if the rest of that block is all
  0xFF; else the next free block.
- **A block is checked before it is written:** every byte 0xFF (~0.1 ms in place), else it is erased
  again, as an erase cut short leaves a few bytes not 0xFF.
- **Erases are rare:** one when the head opens a block, about one save in six for small edits.

### 1.6 Garbage and compaction

- An object's older versions are dead once a newer one is saved; a block with nothing live in it is
  free.
- **Compaction,** when free blocks run short: the live records of the block with the fewest live bytes
  are written again at the head, as a save of their own, and the block becomes free. Audio is never
  moved.
- **A deleted record** (a header with flag bit 1, no payload) stays only as long as an older version
  of its object is left in the flash; compaction then drops it.
- **SAVE refuses** if it would leave fewer than 2 free blocks once compaction has run: compaction
  always needs room to move into. The screen says what to delete (UI proposal, section 8).

## 2. Names, numbers and bits

- **Names use 6 bits a character:**

  | Code | Character |
  |---|---|
  | 0 | space (also the padding) |
  | 1-26 | `A`-`Z` |
  | 27-36 | `0`-`9` |
  | 37-48 | `:` `.` `-` `?` `\|` `/` `\` `*` `#` `$` `@` `%` |
  | 49-62 | spare |
  | 63 | (a name's first character: the slot or the sample entry is empty) |

  An instrument's name (10 characters) takes 60 bits, a cartridge's (12) 9 bytes, a song's (16) 12
  bytes.
- **Numbers:** cartridges, patterns and songs `00`-`FF`; samples `00`-`3F` within their cartridge.
- **Bit-packed fields** follow each other from bit 0 of their first byte upward, in the order listed;
  a field's own bits likewise, least significant first. Spare bits are written 0 (13).
- **Multi-byte numbers** are little-endian.

## 3. Patterns

- **A shared pool** of 256 patterns, `00`-`FF`. Song positions and FUSION slots refer to them, so two
  songs, or a song and a FUSION instrument, can use the same pattern.
- **Size:** 1-16 tracks (`00`-`0F`) and 1-256 rows (`00`-`FF`), set for each pattern. 16 is the
  most because the FM-1 sounds at most 16 voices.
- **A cell** is one track's entry in one row: a note (`C-4`; `---` none; `===` note off), an
  instrument (`0B:05`), a volume (`7F`) and **up to four commands** (`A04`, `ACC`). Trackers call
  them effects; here they are commands (CMD), since FX means the audio effects.
- **Every tracker cell fits:** a MOD, S3M or XM cell becomes one cell, its effect and an XM volume
  column's effect as two commands (4.1).

A pattern record (kind 0x20, number `00`-`FF`):

| Bytes | Field |
|---|---|
| 0 | tracks, 1-16 |
| 1 | rows − 1 (1-256 rows) |
| 2 | EDIT STEP, 0-16 |
| 3-4 | the tracks stored in this record, a bit each (empty tracks take nothing) |
| 5- | one stream for each stored track, in track order: its cells in row order, then 0x00 |

### 3.1 A cell's bytes

A head byte, then the fields it announces, in this order:

| Head bits | Meaning |
|---|---|
| 7 | a note: 1 B, MIDI 12-127 (`C-0` to `G-9`); 0x01 a note off (`===`) |
| 6-5 | the instrument: 00 none; 01 the same as this track's last one in this record (0 B); 10 that one's cartridge, another slot (1 B: the slot); 11 cartridge and slot (2 B) |
| 4 | a volume: 1 B, `00`-`7F` |
| 3 | commands (section 4): one is 2 B, its code and its value; 2-4 are the code 0xFF, their count, then each as code and value |
| 2-0 | rows skipped since this track's previous cell (from row 0 for the first): 0-6; 7: a byte follows with 0-255 |

- **A cell has at least one field,** so a head byte of 0x00 ends the track's stream.
- **The instrument's first appearance** on a track in a record is always written in full (11).
- **No instrument:** the note plays with the track's current instrument, as in XM.
- **Volume:** `7F` plays the instrument at its own level; no volume, the instrument's default.
  Volumes of 0-64 (MOD, S3M, XM) convert exactly both ways: v becomes 2v, 64 becomes `7F`; back,
  round(u × 64 / 127).
- **A cell takes 2 to 15 bytes** (16 after a long skip): 7 at most with one command. So one track's
  stream stays under 4 KB, within one record.

### 3.2 Parts, sizes and reading

- **A pattern too big for one record** is split between tracks into as many parts as it needs (sub
  0-15); every part repeats bytes 0-2, with its own track bits. A track's stream always fits in a
  part, so 16 parts are always enough: a pattern of 16 × 256 cells, every one full with one command,
  is ~28 KB in 8 parts; with four commands each, ~61 KB in 16.
- **Measured on six songs** (two converted modules, four written for PT/FM; 121 patterns): 81.8 KB, 3.4 B a
  cell; the largest pattern 1.76 KB; 675 B a pattern on average, about 6 to a block. That is 9 % less
  than packing row by row (a mask of tracks for each row), and 21-23 % less on sparse songs of 10-12
  tracks.
- **Reading a row** means advancing each track's stream to it: a jump into a pattern scans at most
  ~4,000 cell heads (~0.1 ms). The player keeps a cursor for each track.

### 3.3 FUSION patterns

- **Row = MIDI note:** row *r* plays for the note *r* (`C-4` is row `3C`). A pattern of 128 rows
  (`00`-`7F`) covers every note.
- **Rows as a workspace:** rows no key or song reaches keep ideas for later. Rows `00`-`0B` (below
  `C-0`) and `80`-`FF` never play.
- **No nesting:** a FUSION row that names a FUSION instrument is silent.
- **EDIT STEP 0:** a pattern made from a FUSION slot starts with EDIT STEP 0, so the cursor stays on the
  key's row while its layers are written; every other new pattern starts with 1.

## 4. Commands

A command is a code and a value, a byte each. A cell holds up to four; they run in their order, and a
converted XM cell lists its volume column's first, as FastTracker 2 runs them. The note editor names
each and says its value in words (`SLIDE`, `ACCENT`, `ARPEGGIO 0 4 7`), by its code and, for
0x40-0x7F, by the engine of the track's instrument. The grid shows a command in 3 characters (UI
proposal, 6.2): a tracker effect as its letter and value (`A04`), an XM volume column's as `~` with
FastTracker 2's sign and digit (`~-4`), PT/FM's own by name (`ACC`), every other by its group's sign
and value (`*40` a parameter, `=70` the mixer, `#3C` the FX).

| Codes | Group | Scope |
|---|---|---|
| 0x00-0x3F | tracker effects, with XM's own numbers | the track; global ones marked |
| 0x40-0x7F | the instrument's parameters, a table for each engine | the track |
| 0x80-0xBF | the track's mixer; the FX | the track; the FX global |
| 0xC0-0xFF | PT/FM's own | as listed |

### 4.1 Tracker effects

XM's effects, as XM players run them, so MOD, S3M and XM songs convert without loss.

- **The player runs them with IBXM's code** (BSD-3-Clause), extended: a cell's commands run in turn
  through its handlers; the pitch, volume and pan they make each tick drive whichever voice the track
  plays, a synth's as a sample's; the codes from 0x40 up go to the engines, the mixer and the FX.
- **IBXM is extended freely where PT/FM needs it,** each extension marked in its code. Among them,
  two effects upstream IBXM ignores, played as FastTracker 2 plays them:
  - `E3x` GLISSANDO: on (x not 0), a slide to the note (`3xx`, `5xy`, `~Mx`) is heard in semitones,
    on the note's finetune, while it slides smoothly underneath;
  - `E5x` FINETUNE: at the note's start, -8 to +7 in 1/8 semitones.
- **Upstream IBXM is the test:** a converted song must render as upstream IBXM renders the original
  file, sample for sample with sample instruments, except where an extension plays what upstream
  IBXM leaves out (a song using `E3x` or `E5x`); the test lists those.

| Code | Shown | Name | Notes |
|---|---|---|---|
| 0x00 | `0xy` | ARPEGGIO | |
| 0x01, 0x02 | `1xx` `2xx` | PORTA UP, PORTA DOWN | |
| 0x03 | `3xx` | TONE PORTA | slide to the note |
| 0x04 | `4xy` | VIBRATO | |
| 0x05, 0x06 | `5xy` `6xy` | TONE PORTA + VOL SLIDE, VIBRATO + VOL SLIDE | |
| 0x07 | `7xy` | TREMOLO | |
| 0x08 | `8xx` | PAN | the track's pan, as the MIXER's |
| 0x09 | `9xx` | SAMPLE OFFSET | × 256 samples, from the instrument's START |
| 0x0A | `Axy` | VOL SLIDE | |
| 0x0B | `Bxx` | JUMP | global: to a song position |
| 0x0C | `Cxx` | VOLUME | |
| 0x0D | `Dxx` | BREAK | global: to a row of the next position; the row in hex, as the row numbers (`D20` is row `20`, `00`-`FF`); converters rewrite MOD, S3M and XM's decimal (`D32` becomes `D20`) |
| 0x0E | `Exy` | extended: FINE PORTA UP / DOWN, GLISSANDO, VIBRATO WAVE, FINETUNE, LOOP, TREMOLO WAVE, RETRIG, FINE VOL UP / DOWN, NOTE CUT, NOTE DELAY, PATTERN DELAY | PATTERN DELAY global |
| 0x0F | `Fxx` | TICKS (value below 0x20), TEMPO (0x20-0xFF); `F00` back to the song's own tempo and ticks | global |
| 0x10, 0x11 | `Gxx` `Hxy` | GLOBAL VOLUME, GLOBAL VOL SLIDE | global |
| 0x14 | `Kxx` | KEY OFF | |
| 0x19 | `Pxy` | PAN SLIDE | |
| 0x1B | `Rxy` | MULTI RETRIG | |
| 0x1D | `Txy` | TREMOR | |
| 0x1E | `Uxy` | FINE VIBRATO | S3M's, with no XM twin; IT's letter |
| 0x21 | `Xxy` | EXTRA FINE PORTA | |
| 0x22 | `Yxy` | PANBRELLO | IT's, with no XM twin; IT's letter |
| 0x24, 0x25 | `~-x` `~+x` | VOL SLIDE DOWN, UP | XM's volume column, as it runs there (no memory) |
| 0x26, 0x27 | `~Dx` `~Ux` | FINE VOL DOWN, UP | XM's volume column |
| 0x28, 0x29 | `~Sx` `~Vx` | VIBRATO SPEED, VIBRATO DEPTH | XM's volume column |
| 0x2A | `~Px` | PAN | XM's volume column |
| 0x2B, 0x2C | `~<x` `~>x` | PAN SLIDE LEFT, RIGHT | XM's volume column |
| 0x2D | `~Mx` | TONE PORTA | XM's volume column |

A code's letter is its number in the digits 0-9 and A-Z, as in XM. XM's volume-column effects take a
digit, 0-F, and are shown with FastTracker 2's signs after a `~`.

XM's envelope position (`L`) is not kept: sample instruments have envelopes of the DX7's form (5.4),
so XM envelopes convert approximately anyway.

### 4.2 Time

- **A song has TEMPO, TICKS A ROW and ROWS A BEAT.** A row lasts TICKS A ROW ticks; a tick lasts
  2.5 s / TEMPO, as in trackers. Effects (slides, vibrato, retrigger, delay, cut) work tick by tick.
- **The musical tempo** the screens show is TEMPO × 24 / (TICKS A ROW × ROWS A BEAT): with the
  defaults, 6 ticks and 4 rows a beat (a row is a 1/16 note), it is TEMPO itself. A module at another
  speed converts exactly, and shows its musical tempo (speed 3 at 125 shows 250).
- **TICKS** (`F01`-`F1F`) changes the row's length and keeps the tick's; **TEMPO** (`F20`-`FFF`) changes
  the tick's. `F00` returns to the song's own.
- **SWING** lengthens the first row of each pair and shortens the second, by stretching their ticks.
- The metronome, DELAY times, GATE rates, JAM's quantize and the punch-in loops follow the beat that
  the tempo and ROWS A BEAT give.

### 4.3 The instrument's parameters (0x40-0x7F)

A table for each engine, up to 64 codes each. A parameter command sets its value from its row on,
acts on the track's sounding notes as turning the knob would, and stays until changed; a new
instrument on the track drops it. A sweep is a command on every row (the editor's INTERPOLATE fills
one in between two values).

- **The value is the parameter's own,** as its slot stores it (5.2-5.4); the note editor says it as
  the edit page does (`DETUNE -3`, `RANGE 8'`, `LFO WAVE SINE`). A value past the range acts as its
  top.
- **The codes follow the slot's order,** with gaps where a regular map reads better.

**TB-303** (0-127 each):

| Code | Parameter |
|---|---|
| 0x40-0x45 | WAVE, CUTOFF, RESONANCE, ENV MOD, DECAY, ACCENT |

**Juno-106:**

| Code | Parameter | Values |
|---|---|---|
| 0x40-0x4F | the 16 sliders in the Juno-106's order: LFO RATE, LFO DELAY, DCO LFO, DCO PWM, DCO NOISE, VCF FREQ, VCF RES, VCF ENV, VCF LFO, VCF KYBD, VCA LEVEL, ENV A, ENV D, ENV S, ENV R, DCO SUB | 0-127 |
| 0x50 | RANGE | 0 16', 1 8', 2 4' |
| 0x51, 0x52 | PULSE, SAW | 0 OFF, 1 ON |
| 0x53 | CHORUS | 0 OFF, 1 I, 2 II |
| 0x54 | PWM SOURCE | 0 LFO, 1 MAN |
| 0x55 | ENV POLARITY | 0 +, 1 − |
| 0x56 | VCA MODE | 0 ENV, 1 GATE |
| 0x57 | HPF | 0-3 |

**DX7:** eight codes an operator, so the hex says which (`0x4x`, `0x5x`, `0x6x`; +8 an operator):

| Code | Parameter | Values |
|---|---|---|
| 0x40 + 8 × (operator − 1), + 0-7 | OUTPUT LEVEL, COARSE, FINE, DETUNE, R1, R2, R3, R4 | 0-99; COARSE 0-31; DETUNE 0-14, 7 none |
| 0x70-0x73 | ALGORITHM, FEEDBACK, OSC KEY SYNC, TRANSPOSE | 0-31 (shown 1-32); 0-7; 0-1; 0-48, 24 none |
| 0x74-0x77 | LFO SPEED, LFO DELAY, LFO PITCH DEPTH, LFO AMP DEPTH | 0-99 |
| 0x78-0x7A | LFO WAVE, LFO KEY SYNC, PITCH MOD SENS | 0-5 (TRI, SAW DOWN, SAW UP, SQUARE, SINE, S/H); 0-1; 0-7 |

The envelope levels, key scaling, the sensitivities and the pitch envelope are edited on the
instrument only.

**Sample instrument:**

| Code | Parameter | Values |
|---|---|---|
| 0x40, 0x41 | START, END | a position: the value × 1/256 of the sample's length |
| 0x42 | LOOP | 0 OFF, 1 FORWARD, 2 PING-PONG |
| 0x43, 0x44 | LOOP START, LOOP END | a position, as START |
| 0x45 | TUNE | 1/128 of a semitone, 0x80 none |
| 0x48-0x4B, 0x4C-0x4F | the envelope's R1-R4, L1-L4 | 0-99 |

START acts from the next note; END and the loop's points move under a sounding note.

### 4.4 Mixer and FX (0x80-0xBF)

- **The track's mixer:** 0x80 LEVEL, 0x81 CHORUS SEND, 0x82 DELAY SEND, 0x83 REVERB SEND, 0x84 DUCK
  AMOUNT. PAN is `8xx`.
- **The FX, global:** a code for every knob: 0x90-0x93 GATE (PATTERN, RATE, DEPTH, SMOOTH), 0x94-0x95
  FILTER (CUT, RESO), 0x96-0x97 DRIVE (DRIVE, TONE), 0x98-0x9A LO-FI (BITS, RATE, DUST), 0x9B-0x9E
  CHORUS (MODE, RATE, DEPTH, MIX), 0x9F-0xA3 DELAY (TIME, FEEDBACK, TONE, PING-PONG, MIX), 0xA4-0xA7
  REVERB (SIZE, DAMP, PRE-DELAY, MIX), 0xA8-0xA9 LIMITER (CEILING, RELEASE), 0xAA-0xAC DUCK (SOURCE,
  DEPTH, RELEASE); 0xAE FX ON and 0xAF FX OFF, the value naming the effect.
- They persist as the knobs do, until changed or until another song starts.

### 4.5 PT/FM's own (0xC0-0xFF)

| Code | Shown | What |
|---|---|---|
| 0xC0 | `ACC` | TB-303 accent |
| 0xC1 | `SLD` | TB-303 slide into the next note |
| 0xC2 | `A+S` | both |
| 0xFF | | not a command: the start of a cell's list of 2-4 (3.1) |

### 4.6 Commands together

- **A cell holds up to four,** each code at most once; they run in their order.
- **Common pairs have one code** (`A+S`), so they take one place and 2 bytes.
- **Parameters persist,** so a command can also go on an earlier row.
- **Global commands** (tempo, jumps, breaks, the FX) work from any track.
- **In FUSION rows,** global commands are ignored, and shown dim: a key's row has no song position.

### 4.7 Room to grow

| Codes | Used | Free |
|---|---|---|
| 0x00-0x3F | 35 | 29: XM's unused letters, then 0x2E-0x3F (room for IT's effects) |
| 0x40-0x7F | each engine's own 64: TB-303 6, sample instruments 14, Juno-106 24, DX7 59 | the rest of each; a new engine gets 64 of its own |
| 0x80-0xBF | 36 | 28: about seven more effects |
| 0xC0-0xFF | 3, and 0xFF for lists | 60 |

Beyond that, the pattern's format version allows a new cell layout (a second code byte after an escape
code), old patterns read as before.

## 5. Cartridges and instruments

### 5.1 A cartridge record

Kind: its type (0x01-0x05); number: the cartridge, `00`-`FF`.

| Bytes | Field |
|---|---|
| 0-8 | name, 12 characters |
| 9 | slots stored: up to the last one used (empty ones before it marked by their name) |
| 10- | the slots, each at its type's fixed size |

A sampler cartridge's record also holds its samples' table (5.5).

- **Every slot has spare bits,** and every full cartridge leaves room in its block (13).

### 5.4 Sample instruments

| Field | Bits |
|---|---|
| SAMPLE: its index among the cartridge's samples | 6 |
| START, END, LOOP START, LOOP END: positions in the sample | 20 each |
| LOOP: OFF, FORWARD, PING-PONG | 2 |
| BASE NOTE | 7 |
| TUNE, in 1/128 of a semitone, 0x80 none | 8 |
| LEVEL | 8 |
| VOLUME: a module's default volume, 0-64 | 7 |
| the envelope: R1-R4 and L1-L4, as the DX7's | 56 |
| name | 60 |
| spare | 86 |

- **The envelope works as a DX7 operator's:** from silence it moves to L1 at R1, to L2 at R2, to L3
  at R3, and holds L3 while the key is down; at release it moves to L4 at R4.
- **The loop is a sustain loop:** playing goes from START into LOOP START - LOOP END, and repeats it
  while the key is held. At release it goes on from where it is, through the rest of the loop (a
  ping-pong pass going backwards back to LOOP START, then forwards) and on to END, while the envelope
  releases. Nothing jumps, so nothing clicks.
- **A new instrument** plays its sample whole: START 0, END its length, LOOP OFF.

### 5.5 Samples and FUSION slots

- **A sampler cartridge's record** is: name (9 B), instruments stored (1 B), samples stored (1 B), the
  instruments (40 B each), the samples' table (16 B each). A sample's entry: its length in samples
  (20 bits), its rate in Hz (18 bits; an instrument's BASE NOTE plays it at that rate), its coding
  (4 bits: 1 PTR 8-bit, 2 PTR 16-bit), its name (60 bits), spare (26 bits). A sample has no loop of
  its own: loops belong to instruments, and one sample can serve several of them.
- **A FUSION slot:** its pattern (8 bits), name, LEVEL, spare 52.

### 5.6 Deleting

- **Deleting an instrument never deletes its sample.**
- **Deleting a sample** (its cartridge's samples list, SEL → DELETE) warns first: `DELETE SAMPLE?
  3 INSTRUMENTS USE IT AND ARE DELETED TOO`. Accepted, the sample and those instruments are deleted in
  one save; cells that played those instruments point at empty slots (section 10).
- **CLEAN UP** (SETTINGS → TOOLS) also deletes samples no instrument uses.

## 6. Sample audio (PTR)

**PTR** (PT/FM Rice) codes 8-bit and 16-bit samples losslessly. A sample's audio is a record of its
own: kind 0x10, number its cartridge, sub its index there.

| Bytes | Field |
|---|---|
| 0 | coding: 1 PTR 8-bit, 2 PTR 16-bit |
| 1-3 | length in samples |
| 4- | the index: the offset of every 16th block from the payload's start (u32 each), then every block's coded length (u16 each) |
| then | the blocks |

- **Samples** are signed (two's complement), 8 or 16 bits.
- **A block** is 256 samples (the last one fewer), counted from the sample's first, and decodes on its
  own. It is one stream of bits, read from each byte's most significant bit, padded to a whole byte
  at its end:
  - a mode byte: a predictor order 0-3, or 7 for raw;
  - raw: the samples as they are (8 or 16 bits each);
  - else the first *order* samples as they are, then for each further sample the prediction's error
    e = x − (0 | x1 | 2x1 − x2 | 3x1 − 3x2 + x3), as u = 2e (e ≥ 0) or −2e − 1, in partitions of 64:
    a Rice parameter k (4 bits for 8-bit samples, 5 bits for 16-bit), then every u as (u >> k) zeros,
    a one, and its k low bits. The parameter's highest value (15, or 31) stores the partition's u
    plainly instead (12 bits each for 8-bit samples, 20 for 16-bit).
- **Playing from anywhere** (START, a loop's start): the index finds the block, decoded from its
  start: at most 255 samples more, once a jump.
- **The index** costs 2.25 B a block, against 4 for a plain offset each.
- **Measured:**
  - 8-bit: 41-67 % of their raw size for a module's samples, 33 % for 94 drum and instrument samples;
  - 16-bit: 50 % for the same 94 (13-88 % each); whole recordings, with their quiet tails, 34 %;
  - so a 16-bit sample takes 3 times the flash of the same sound at 8 bits;
  - decoding on the FM-1: ~0.24 us a sample (8-bit).
- **Fixed predictors are enough:** a linear predictor (FLAC's kind) would save ~7 % on 16-bit samples
  and under 2 % on 8-bit ones, for ~8 more multiply-adds a sample in the audio interrupt.
- **8 or 16 bits:** a converter keeps the sample's depth, except that audio whose low byte is always
  0 (an 8-bit sound in a 16-bit file) is stored as 8-bit: as 16-bit it would take 3 times the room.
- **Placement** (by the uploader): the fast regions first, by priority (most played, or smallest);
  else the slot, where the current song's samples are cached in RAM while they fit (section 11) and
  the others are read with direct reads as they play.
- **Samples come only from the PC.** On the device the only change to one is deleting it (5.6).

## 7. Songs

Kind 0x21, number `00`-`FF`; the list on SONGS is in numbers' order. Nothing refers to songs, so moving
one needs no reference update.

| Bytes | Field |
|---|---|
| 0-11 | name, 16 characters |
| 12-13 | TEMPO, 32-300 |
| 14 | TICKS A ROW, 1-31 |
| 15 | ROWS A BEAT, 1-16 |
| 16 | SWING, 50-75 (%) |
| 17 | flags: bit 0 AT THE END = STOP (else LOOP); bit 1 linear slides (else Amiga periods); bit 2 fast volume slides |
| 18 | LOOP FROM: the position the song loops to (0 unless a module set it) |
| 19 | the global volume at the start, 0-64 |
| 20 | positions − 1 (1-256) |
| 21- | the order: a pattern number for each position |
| then | the mixer: tracks stored (0-16, up to the last that differs from the default), then for each LEVEL, PAN, DUCK, CHORUS SEND, DELAY SEND, REVERB SEND (a byte each, below) |
| then | the FX setup, 44 B (below) |
| then | spare, 8 B |

**A track's mixer bytes** (songs, the jam, and the commands 0x80-0x84 and `8xx`): LEVEL `00`-`7F`,
`7F` the track at full level, as a cell's volume; PAN `00` left, `80` centre, `FF` right; DUCK and
the three SENDS `00`-`7F`, `00` none. The default: LEVEL `7F`, PAN `80`, the rest `00`.

**The FX setup** (songs and the jam):

| Bytes | Field |
|---|---|
| 0 | ROUTING: GLOBAL or SENDS |
| 1-5 | the chain's order: 9 items (the 8 effects of the chain and ◆ SENDS), 4 bits each |
| 6-7 | on / off: the 8 chain effects, DUCK, METRONOME |
| 8-36 | the knobs, a byte each, as its step from the bottom of its range (UI proposal, 6.6: FILTER's CUT 0-127 with OFF at 64, a % knob 0-100): GATE 4 (its PATTERN among them), FILTER 2, DRIVE 2, LO-FI 3, CHORUS 4, DELAY 5, REVERB 4, LIMITER 2, DUCK 3 |
| 37-43 | METRONOME: TEMPO (2 B: 0 FOLLOW, else 30-300), BEATS A BAR, SOUND, LEVEL, COUNT-IN; spare |

- **Size:** ~150 B for 20 positions and 10 tracks; at most ~430 B.
- **Converted modules keep their sound:** TEMPO and TICKS A ROW from their BPM and speed, the pans from
  their channels (MOD's left, right, right, left; S3M's pan table), their global volume and restart
  position, and their slides' kind: Amiga periods for MOD and S3M, linear for XM; S3M files saved
  for fast volume slides (Scream Tracker 3.00, or their header's flag) keep them. Our own songs slide
  linearly and normally.
- **Not in a song:** mutes and the punch-in effects (performance only).

## 8. The jam

Kind 0x22, number `00`: the current jam, kept by SAVE like any change.

| Bytes | Field |
|---|---|
| 0 | LENGTH: 1, 2 or 4 bars |
| 1-2 | TEMPO, as a song's |
| 3 | TICKS A ROW |
| 4 | ROWS A BEAT, the grid: 4 for 1/16, 6 for 1/16T, 8 for 1/32 |
| 5 | SWING |
| 6 | QUANTIZE |
| 7-8 | KIT: cartridge, first slot |
| 9 | the arpeggiator's mode |
| 10-17 | the live tracks' 4 instruments: cartridge, slot |
| 18-89 | the mixer: the 8 lanes and the 4 tracks, LEVEL, PAN, DUCK and the 3 SENDS (6 B each, as a song's) |
| 90-133 | the FX setup (section 7): the jam has its own, METRONOME included |
| 134-141 | spare |
| 142- | the loop: a pattern payload (section 3) of 12 tracks, the 8 drum lanes then the 4 live tracks; rows: the bars × the grid |

- **A drum lane is a track:** a step that is on is a cell with a note (`C-4`; a sample instrument's
  BASE NOTE), its level the cell's volume, its ratchet a retrigger, `E9x`: x = TICKS A ROW / the hits,
  so the hits are those that divide TICKS A ROW (×2, ×3, ×6 at 6). Storing the jam into
  a pattern (ENV in JAM: each lane and track used becomes a track, 8 + 4 ≤ 16) is a copy, and so is
  loading a pattern into the jam.
- **The live tracks** hold the notes recorded, quantized to the grid, with their note offs.
- **Not stored:** mutes, the latch, what is playing.
- **Size:** ~1-2 KB for a full jam of 4 bars. A denser one is split as a pattern is (3.2): part 0
  holds bytes 0-141 and the loop's first tracks, the next parts the loop's other tracks.

## 10. References and integrity

**What refers to what:** a cell to an instrument (cartridge:slot); a song position and a FUSION slot to
a pattern; a sample instrument to a sample of its cartridge; the jam to its kit (a cartridge and its
first slot) and its 4 live instruments.

**MOVE, SWAP or DELETE** of an instrument, a cartridge, a pattern or a sample asks first (UI proposal,
section 8):
- **YES:** everything pending is saved; then the change and every record it touches (patterns, songs,
  cartridges, the jam) are written as one save. A power cut leaves the state before or the state
  after, never a mix.
- **NO:** the references stay as they are. One that points at nothing is drawn red and plays nothing.
- **Finding them** decodes every pattern's instruments in place, and reads the songs, the FUSION and
  sampler cartridges and the jam: a few milliseconds for a full store.
- **The cost:** an instrument used in 40 patterns ~0.3 s; the most, a cartridge used in every pattern,
  ~2 s, with a progress bar (section 11).

**Integrity:**
- At power-on every record in the fast regions is checked (1.4). A record that fails falls back to
  its older version if the flash still holds one; else its object is missing. STATUS → STORAGE lists
  either.
- CHECK REFERENCES lists references to nothing; CLEAN UP deletes unused patterns, instruments and
  samples; CHECK STORAGE reads and checks everything, the slot's audio included.

## 11. Editing, saving and RAM

- **Changed records stay in RAM, packed, until SAVE.**
  - A pattern is edited in its packed form: an edit encodes the changed track's stream again (under
    4 KB, usually far less), so no unpacked copy of a whole pattern is needed.
  - Changed instruments are kept as their slots (at most 112 B each); SAVE writes them into their
    cartridge.
- **The edit memory** shares 63 KB with the RAM cache of slot samples: edits always have at least
  32 KB and may grow to all 63 KB, the cache giving way (those samples are then read as they play). Full:
  `MEMORY FOR EDITS IS FULL` (UI proposal, section 8).
- **UNDO** keeps the older copy of what the last edit changed: a track's stream, a block's tracks (at
  most a pattern), a slot, a song. It never reaches past a SAVE or a reference update.
- **REVERT** (SAVE + OCT-) drops the edit memory and reads everything from the flash again; it writes
  nothing.
- **SAVE** waits for a pause, then writes every changed record as one save (1.3), compacting first when
  free blocks run short.

**Where the RAM goes:** of the 512 KB, about 432 KB hold data; the rest is code that runs while the
flash is busy, the stacks, and the boot's own. The sizes are those of the same engines, effects and
screen as built for the FM-1.

| What | KB |
|---|---|
| the screen's strip (half the screen) | 60 |
| the DX7's tables | 28 |
| 16 voices, the scopes, the mixing | 25 |
| the effects but DELAY: REVERB 50, CHORUS 8, the sends 6, the rest 1 | 65 |
| USB and seeding, the store's map (1.4), a save's pages | 14 |
| the screens' and the player's state | ~30 |
| the DELAY line: 1 s at 29.4 kHz, so a 1/4 note down to 60 BPM (PING-PONG: 0.5 s) | 59 |
| the punch-in buffer: the last 0.5 s in stereo, so a beat at 120 BPM and faster | 88 |
| the edit memory and the cache of slot samples | 63 |

Where a note value does not fit (a DELAY TIME, a punch-in loop), the longest one that does is used.

**The REVERB and the DELAY run at 2/3 of the output's rate, 29.4 kHz,** resampled in and out; what
they give back keeps everything up to ~13 kHz. At half the rate the loss above 11 kHz is plain to
hear; 29.4 kHz is close to the full rate by ear.
- **The REVERB** is a plate (Dattorro's, UI proposal 6.6): its delay lines take 44.5 KB at 16 bits
  (67 KB at the full rate) and PRE-DELAY's (up to 100 ms) 5.9 KB.
- **The DELAY** is one line, 59 KB (88 KB at the full rate), fed one signal: the sends are mono, and
  in GLOBAL routing the mix is summed into it. PING-PONG reads it at the time and at twice the time
  (the repeats two lines would give), so its time is at most half the line.

**What writing costs** (section 1's figures; an erase only when a block opens or compaction runs):

| Action | Written | Programs | Erases | Time |
|---|---|---|---|---|
| a cell changed, SAVE | 1 pattern, ~0.7 KB | 3-4 | 0, or 1 when a block opens (~1 save in 6) | ~8 ms |
| a song's order, or the settings | ~150 B | 1 | 0-1 | ~2 ms |
| a DX7 voice changed | its cartridge, 3.6 KB | 14 | 0-1 | ~27-45 ms |
| the jam | ~2 KB | 8 | 0-1 | ~16 ms |
| a busy session: 20 patterns, a cartridge, a song | ~18 KB | ~72 | ~5 | ~0.2 s |
| compacting a block | its live records, at most 4 KB | at most 16 | 1 | at most 45 ms |
| a reference update: an instrument in 40 patterns | ~27 KB | ~110 | ~7 | ~0.3 s |
| the most: a cartridge used in all 256 patterns | ~175 KB | ~700 | ~43 | ~2 s |

- **Only three things write several blocks:** reference updates (asked for, and rare), compaction,
  and seeding from the PC.
- **Wear:** a normal SAVE costs ~0.2 erases, shared by the blocks that hold no audio: the head walks
  every free block in turn. With audio filling the fast regions down to the reserve, 16 blocks are
  left turning; a thousand saves a day then give each ~12 erases a day, and its ~100,000 last over
  20 years. Less audio in the fast regions, more blocks, longer.

## 12. The data blob, seeding and converters

A data blob holds records in the device's own formats. A page writes it to the device; nothing
converts on the way.

### 12.1 The blob

- **One file holds every record** the device should have, each exactly as the device stores it. The
  uploader never changes a payload; it only decides where it goes.
- **No flash addresses:** records are placed when seeding, against the layout the device reports
  (12.2), so one blob works with every firmware that accepts its kinds and versions.
- **One blob for both:** the real FM-1 and the emulator.

A header, a table of records, then their payloads (each starting at a multiple of 4).

| Header bytes | Field |
|---|---|
| 0-7 | magic `PTFMDATA` |
| 8-9 | the blob format's version (1) |
| 10-11 | records, N |
| 12-15 | the blob's length |
| 16-19 | CRC-32 of bytes 32 to the end |
| 20-31 | spare |

| Entry bytes (N × 32) | Field |
|---|---|
| 0-3 | kind, number, sub, version |
| 4 | placement: 0 a record (the fast regions only); 1 audio (the fast regions first, then the slot) |
| 5 | priority: for audio, which goes into the fast regions first |
| 6-7 | spare |
| 8-11 | the payload's offset in the blob |
| 12-15 | its length |
| 16-19 | its CRC-32 |
| 20-31 | label, ASCII, for the page only |

The record header (1.2) is made when the blocks are laid out, with the save number.

**Checks:**
- **the uploader:** the magic, the format's version, the blob's CRC and every payload's; no (kind,
  number, sub) twice; every (kind, version) one the device accepts (12.2);
- **the device:** every block read back as it is written; every record's CRC at power-on (1.4).

### 12.2 Seeding

- **Who seeds:** `dist/seed.html` seeds the FM-1 over USB-MIDI (Web MIDI, in Chrome or Edge); the
  emulator's Seed button seeds the emulated one. One seeding module (JavaScript) serves both pages;
  only the transport differs: SysEx through Web MIDI, or function calls into the WebAssembly. The
  device's side is the firmware's own code in both.

1. **The device reports its layout:** its firmware and protocol versions; where its firmware ends; the
   regions; the reserve; the (kind, version) pairs it accepts; the largest message it takes; and its
   records: kind, number, sub, version, CRC, place, save number.
2. **The uploader plans:** a record already on the device with the same CRC stays where it is; new and
   changed ones go into free blocks, records packed together, audio by priority; the reserve stays
   free; records the device has and the blob does not get deleted records, so the device ends up
   holding exactly the blob. It shows the plan: each region's space, what goes where, what does not
   fit, and **what will be deleted**, the device's own saved work among it. Writing starts only once
   the user accepts the plan; keeping a copy of that work is the user's to do. It stops there if a
   record does not fit in the fast regions, or the device does not accept a (kind, version).
3. **It writes the blocks** as one save: the device's last save number + 1, the last record flagged.
   For each block the device erases it if it is not all 0xFF, programs it, reads it back and answers.
   The uploader waits for every answer: an erase takes tens of milliseconds, and MIDI has no flow
   control.
4. **The device mounts** and answers with the result.

- **The uploader owns placement.** The device does not allocate; it checks that every block written
  lies in a region it reported.
- **A seeding cut short** leaves the previous library whole as long as the new records went into free
  blocks: they count only once the last one is written. Only a full rewrite into a full flash can leave
  a part; seeding again mends it.
- **While seeding,** the device silences audio (an erase stops code fetches) and does not read the
  store. After 10 s without a message it ends the seeding and mounts what is there.
- **After a firmware install** only the slot's audio is missing; the uploader sees it in the layout and
  writes only that.
- **The device refuses to be seeded with edits not saved:** `SAVE OR REVERT FIRST`.

**Messages:** SysEx `F0 7D 50 54 cmd payload F7`.
- `7D` is the manufacturer ID for non-commercial use, open to anyone: right for free firmware. A
  registered ID is needed only for a product that is sold.
- `50 54` ("PT") marks PT/FM's messages among others on `7D`. Every PT/FM protocol shares it; the
  command byte tells them apart, and seeding's are those below.
- The payload is 7-bit packed, 7 bytes in 8; at most 512 B of data a message, which keeps a frame
  under the firmware's 640 B USB-MIDI limit.

| cmd | Direction | Contents |
|---|---|---|
| 01 HELLO | uploader → device | the protocol's version |
| 02 LAYOUT | device → uploader | the layout (step 1), in several messages if long |
| 10 BEGIN | uploader → device | the save number, the number of blocks to write |
| 11 CHUNK | uploader → device | block, offset, up to 512 B of the block's bytes |
| 12 BLOCK | uploader → device | block, CRC-32 of its 4096 B: erase if needed, program, verify |
| 13 END | uploader → device | mount, and answer with the result |
| 1F ABORT | uploader → device | stop, and mount what is there |
| 20 ACK | device → uploader | the command and block it answers, and a result code (0 = done) |

In the emulator the same bytes pass through a function call each way, so the device's code and the
uploader's are both exercised.

### 12.3 Making blobs, and converters

- **The packer** (`tools/`) builds the demo data's blob from `demo-disk/` (its JSON and FLAC files,
  [../../demo-disk/README.md](../../demo-disk/README.md)), and again whenever the demo data changes.
  It makes every record of this proposal: cartridges from the banks, PTR audio and sampler cartridges
  from the sample sets, patterns and songs from the songs. Other data sets are made into blobs by the
  same tool, outside this repository.
- **Converters** turn other formats into these records: MOD, S3M and XM into a song, its patterns, a
  sampler cartridge and PTR audio; `.syx` into DX7 cartridges and back; Juno-106 dumps into Juno-106
  cartridges and back; WAV and FLAC into PTR audio and an instrument.

## 13. Extending

- **A new kind of record** takes a new kind code; a new layout of a kind takes the next version.
- **A device keeps the records it does not know:** it does not read them, and compaction moves them as
  they are, byte for byte.
- **Spare bits and bytes** are written 0, and a meaning given to them keeps 0 as "as before", so a new
  parameter in a slot's spare bits needs no new version.
- **Larger slots** are a new version of their kind; every full cartridge leaves room in its block.
- **Reserved:** name code 63 (an empty slot or sample entry), kind 0xFF (erased flash), command code
  0xFF (a cell's list of commands).
