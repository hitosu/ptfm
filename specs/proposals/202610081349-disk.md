# Proposal: disks

Status: **settled** (2026-10-09); the spec: [../files/disk.md](../files/disk.md), which leads from now
on. Kept as the record.

A **disk** is a plain file on a computer that stores a set of PT/FM's files, to be passed on:
cartridges and their samples' audio, patterns, songs, the jam, the settings. The demo data is a disk.
The web editor (to come) opens and saves disks; sending updates to the device is the editor's, not
the disk's. The device itself never reads a disk.

**Files** here are the files proposal's records ([202610080050-fs.md](202610080050-fs.md), 1.2): a
file on a disk is a record's payload, byte for byte, so nothing converts between a disk and the
device.

## 1. The file

A 16-byte header, then the files one after another; nothing else. Named `<name>.ptd`.

| Bytes | Field |
|---|---|
| 0-7 | magic `PTFMDISK` |
| 8 | the container's layout: 1 |
| 9-11 | spare, 0 |
| 12-15 | the number of files |

**A file:** a 12-byte header, then its payload; the next file starts at the next multiple of 4, the gap
written 0.

| Bytes | Field |
|---|---|
| 0 | type: the record's kind (the files proposal, 1.2) |
| 1 | number |
| 2 | sub |
| 3 | the type's version |
| 4-7 | the payload's length |
| 8-11 | CRC-32 of the payload |

- **Each (type, number, sub) at most once.**
- **Objects are whole:** a pattern with all its parts, the jam with all its parts, a sampler
  cartridge with its samples' audio.
- **Any set:** a whole library, one cartridge, or a song with its patterns, cartridges and audio.
  References may point at files the disk does not hold (a song without its cartridges).
- **Order:** settings, cartridges, songs, patterns, the jam, notes, then the audio, each by number and
  sub.

**Types only a disk holds** (0xE0-0xEF), never sent to the device:

| Type | What | Payload |
|---|---|---|
| 0xE0 | notes | text, UTF-8: what the disk holds, its credits and licences |

A disk whose works ask for their notice to travel with them (MIT, CC BY) holds it in its notes.

**Size:** a whole library is under 1 MB, as the FM-1's flash is.

## 2. Versions

- **Each type has its own version,** in every file's header, as in every record in the flash (the
  files proposal, 1.2, byte 3). A new layout of a type takes its next version (the files proposal,
  section 13); the other types keep theirs.
- **The editor reads every version of a type there has been** and saves the current one, so an older
  disk is upgraded when it is opened. The converters live there, on the PC, and cost the device no
  flash.
- **The device reads the current version of each type.** It reports the versions it accepts (the files
  proposal, 12.2), and the editor sends only those.
- **A file of a version newer than the editor knows** is kept as it is, shown, and not sent: the
  editor says to update itself.
- **The container's layout** (header byte 8) is the disk's own; it changes only if the header or the
  file headers do.

## 3. The demo disk

- **`demo-disk/`** holds the demo disk's sources: patch banks, sample sets and songs as JSON and FLAC
  files, each with its licence ([../../demo-disk/README.md](../../demo-disk/README.md)), and the tools
  that make them (`demo-disk/tools/`).
- **The playground has the demo content built in** (`tools/gen_playground.py` makes
  `playground/content.js` from these sources); it knows nothing of disks. Only the editor and the
  firmware work with disks' files.
- **The packer** (`tools/`) will build `dist/demo.ptd` from them, committed with the other built
  files. Its notes hold `demo-disk/CREDITS.md`.
