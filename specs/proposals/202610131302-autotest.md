# Proposal: autotests, MIRROR and the debug page's runs

Status: **settled** (2026-10-13); its specs are written and lead from here: MIRROR and the state in
[../connections.md](../connections.md#mirror-the-panel-from-a-page), the autotests, the debug page's runs,
the test tone and the bench in [../debug.md](../debug.md#autotests). Kept as the record. Where a detail says
*(a default)*, it was not decided on its own and can change when tried.

**Autotests** play the FM-1 as a hand on its panel would: the debug page presses its buttons and keys and
turns its knobs over USB-MIDI, waits, checks where the FM-1 is, and measures. They run on the real device
and its real sound, scenario after scenario, unattended but for a few prompts. The first ones are **stress
tests** (the heaviest songs, the keys' voices, the effects, DJ, USB audio); **UI tests** come later (every
screen opened, patterns edited, screenshots compared).

What goes where:

- **The scenarios live on the page,** not in the firmware: they are steps of panel input, so they change
  without a new firmware, and they run on any PT/FM firmware.
- **The firmware gets two small things, in every build:** **MIRROR**, its panel driven from MIDI, and a
  **state query**, so the page checks where the FM-1 is before each step.
- **The debug build** measures as before (FIGURES), keeps only what needs its insides (the chip's own costs,
  each engine and effect alone), and gets a test tone for USB audio.

## 1. MIRROR: the panel from MIDI

PT/FM takes the PT/FM controller's mirror messages ([../controller.md](../controller.md#2-mirror-mode)) as its
own panel: a press from MIDI is a press, with every combination, hold and layer the FM-1's own has.

| Message (the channel MIRROR listens on) | Is |
|---|---|
| Note On 53 + k (velocity > 0); Note Off 53 + k, or Note On at velocity 0 | key k (0-26, F3-G5) held; let go |
| CC 102 + id, 127 / 0 | button id (0-13, the firmware's ids: OCT- 0 ... REC 13) held; let go |
| CC 20 + id | knob id (0-6: SELECT, ALGORITHM, K1-K4, PRESETS) turned: 1-63 that many clicks clockwise, 65-127 128 minus that many back |
| CC 7 | MASTER, 0-127 |

- **It switches on with the controller's hello,** `F0 7D 50 54 43 02 00 <version> <channel> F7` (mode 0,
  mirror), arriving over USB: from then on, that channel's messages from USB are the panel. Nothing is set
  on the device; another channel, and the jack, work as before.
- **It switches off** with a hello of mode 1 (`... 43 02 01 ...`), at a USB bus reset (unplugged, the
  computer restarting) and at power-off. *(a default)*
- **At every hello,** on or off, every control MIRROR holds is let go, so nothing stays pressed.
- **MIRROR's messages are only the panel:** they are not notes, not learned controls (MIRROR comes first on
  its channel, before any mapping), not MIDI OUT's; the MIDI IN CHANNEL setting does not apply to them.
- **A press shorter than a main loop pass is not lost:** a press and its release that come between two passes
  are seen as a press, then a release, as MIDI learn's controls already are.
- **The FM-1's own panel stays live:** both hands count, so a run is spoiled by touching the FM-1.
- **PT/FM sends no LEDs back** *(a default)*: the page reads the state instead (section 2). A second FM-1
  running the controller, routed through a computer, would mirror too, with its LEDs dark.
- **PT/FM never answers the controller's question** (`43 01`): it is not a controller.

## 2. The state query, in every build

`F0 7D 50 54 40 F7` (**40 STATE?**) asks; the FM-1 answers **41 STATE** from the main loop, packed as
seeding's messages (7 bytes in 8, [../files/blob.md](../files/blob.md#seeding)). Its bytes *(a default)*:

| Field | What |
|---|---|
| the version | of this answer's layout |
| the firmware | its version text and its build: release or debug |
| MIRROR | on, its channel |
| the screen | its name; the overlay on top, if any: a question, a menu, a list, a hold layer, a progress bar (its kind; a question's first line) |
| the screen's cursor | up to 8 bytes whose meaning each screen gives, first for the screens the stress tests use: SONGS the song and the boxed start position; INSTRUMENTS the cartridge and the slot; FX the page and the picked effect; DJ the list's highlight; SETTINGS the page and the line; later every screen's (the EDITOR the pattern, the row, the track, the field) |
| what plays | nothing, a song, a pattern, LOOPS, DJ; playing or not; the song (its number and name), its position and row; the tempo |
| DJ | each deck's song (number and name), playing or not, position; the crossfader; each deck's filter (on, its setting); each LFO (on, its shape, range and speed); SYNC, PREVIEW; the pads' mode |
| the effects | the ones on and working now (the FIGURES bit set) |
| the keys | the instrument they play (cartridge and slot); the octave; ARP on, latched |
| VOICES | the count, and the voices sounding now |
| unsaved | the number of unsaved changes |
| the hold delay | SETTINGS' HOLD DELAY, so the page times its holds |

| the settings scenarios depend on | VOICES, SYNC, KEYS OCTAVE, the METRONOME and the COUNT-IN, USB GAIN |

- **What it costs:** about a kilobyte of code (the screens' cursors included); no RAM kept (the answer is
  built on the main loop's stack when asked); no time unless asked; nothing in the sound's code.
- **Only the page asks.** The release answers it as it answers seeding's messages; the debug build as well.
  It comes from the main loop, so it waits while a progress bar runs (a REVERT's reload, AUTO LEVEL): the page
  allows for that.
- **A firmware from before this proposal** answers nothing: the page says so and runs no autotest.

## 3. What autotests may do

- **They drop unsaved changes before every scenario:** REVERT (SAVE held + OCT-, then OCT+ to the question),
  when the state says there are any. So every scenario starts from what is saved, a run never piles up
  changes until the edit memory is full, and a run stopped half way leaves nothing to clean. Under RUN, small
  and dim: `AUTOTESTS DROP UNSAVED CHANGES: SAVE YOUR WORK FIRST` (no question).
- **They never press SAVE,** and never run what writes the flash outside the edits (a sampler's CLONE or MOVE,
  MOVE TO ROM, FILL ROM, seeding, CHECK STORAGE's repairs): REVERT could not take those back.
- **Everything else is theirs:** screens, the transport, the keys, FX knobs, DJ's stand, the tools that only
  change edits (AUTO LEVEL, RECORD PATTERN), as a hand would.
- **A scenario sets every setting it depends on** (VOICES 16 for sixteen keys, SYNC INTERNAL, the METRONOME
  off, DJ's effects), as edits, and checks them: what is saved can be anything, and REVERT before the next
  scenario takes them back.

## 4. The debug page

`dist/debug/install.html`, three parts:

1. **INSTALL** (the debug package, its CLEAN INSTALL switch on at first, UPLOAD DEMO DISK) and **CONNECT,**
   as now.
2. **RUNS** (was the figures' RECORD and STOP):
   - **RECORD** starts a run under the name in the field; while it records, the field is disabled and shows
     the run's name. **STOP** ends it and leaves the name in the field, ready to edit (`PASS 1` into
     `PASS 2`).
   - **The runs** are a list, each with its length and its CPU at a glance, **COPY** (its report) and
     **DELETE**. The part's **COPY** copies every run's report, one after another, without a summary of
     them all; **DELETE ALL** (was RESET) drops them.
   - **FREEZE SCREEN** and the live figures, as now. RECORD waits while an autotest runs.
3. **AUTOTEST** (was BENCH):
   - **The scenarios** in their groups, each with a tick box; a group's box ticks the group. **RUN** runs the
     ticked ones in order, **STOP** stops: every control let go, the test tone off, all sound off, MIRROR off.
     The warning of section 3 under RUN, and `HANDS OFF THE FM-1 WHILE IT RUNS`.
   - **While it runs:** the scenario and its step, the time left, and the checks so far. **A prompt** stops it
     with its text (`START RECORDING ON THE COMPUTER (USB AUDIO), THEN CONTINUE`) and a **CONTINUE** button.
   - **MIRROR is kept on:** the page sends the hello at RUN, and again whenever the state says MIRROR is off
     (USB was reset).
   - **Each run of autotests makes its own report,** listed with its **COPY** (and **DELETE**), as RUNS'.
   - **On a firmware other than the debug build** it runs the same, checking the state at every step; what
     only the debug build measures is left out of the report, and the scenarios that need it (CHIP, the
     USB tone) are skipped and say so. CONNECT is all it needs: nothing is installed for it.

## 5. A scenario

A list of steps, with checks between them.

- **Input:** a tap (held ~60 ms *(a default)*), a hold (for a time, or past the hold delay the state gave), a
  combination (one control held while others go), keys held and let go, knob clicks (~50 ms apart *(a
  default)*), MASTER. Clicks that come within one main loop pass count as a fast turn, as a hand's do, and
  some knobs then take bigger steps: an exact value is reached by seeking.
- **Seeking:** a knob turned a click at a time until the state shows what is wanted (a song by its name, a
  cartridge, a deck's filter, the crossfader), at most a set number of clicks: the FM-1 is never assumed to
  start where the page thinks.
- **Waiting:** a time, or until the state shows something (`DJ`, both decks playing), at most a set time.
- **Checks:** the state after a step; on the debug build also FIGURES (late halves, the worst half). A check
  that fails ends the scenario (`FAILED: EXPECTED SONGS, FOUND INSTRUMENTS`), all sound off, and the run goes
  on with the next scenario.
- **Measured stretches:** named parts of the scenario whose FIGURES (the debug build) go into the run's
  report, each laid out as a RUNS report is. While one is measured the page sends nothing but FIGURES'
  question once a second, so its own traffic does not weigh on what is measured.
- **Prompts,** for what the page cannot do itself (recording on the computer), and **notes** for the report.
- **Every scenario starts from a known place,** whatever the last one left: HOME tapped until the state shows
  no overlay (a question, a menu, a layer), what plays stopped, ARP off, all sound off (HOME + REC), REVERT
  (section 3); then the screen of its own choosing.

## 7. The USB test tone (debug build)

`F0 7D 50 54 34 <on> F7` *(a default)*: while on, USB audio carries a test tone instead of the mix (a sine of
997 Hz on the left, 1,499 Hz on the right, -12 dBFS whatever USB GAIN is *(a default)*), through the same
resampler and stream.
A recording of it shows every lost, repeated or late packet exactly, and the resampler's quality, apart from
the music. The speaker and the jack play on as before; the tone goes off at a USB bus reset and at
power-off, so it never stays on unseen.

## 8. The firmware's own measurements (debug build)

The bench keeps only what the page cannot do through the panel: **THE CORE** (the chip's own costs) and
**ALONE** (each engine and effect by itself, warm and cold). Its steps with sound (the keys' voices, the
songs, DJ) move to the page's scenarios, measured through FIGURES, and leave the firmware. The page asks
for it as now (32 BENCH, its records 33).

## 9. The reports

- **Plain text,** ASCII, lines under 100 characters, as the figures' report: the firmware and its build, the
  time, each scenario's result (PASSED, FAILED and why, SKIPPED and why), its notes, its measured stretches
  (laid out as RUNS' reports) and CHIP's tables.
- **Later, a bundle:** SAVE writes the report as an HTML file with its screenshots in it; recordings beside
  it as WAV files (about 10 MB a minute). COPY keeps copying the text.

## 10. Later, prepared for

- **UI tests:** scenarios that open every screen, edit patterns, instruments and songs, through the same
  steps and checks.
- **Screenshots (debug build):** asked for, the screen is paused, drawn once more and sent band by band as
  its palette's colour numbers, compressed (a few KB, under a second), then let go; the page makes a PNG.
- **Recording the sound:** the page records the FM-1's USB audio input itself (one permission prompt), a WAV
  a scenario, with a quick look: level, silences, clicks, lost packets. Two debug switches would help: USB
  carrying exactly what the jack plays (PREVIEW split, the METRONOME's clicks, MASTER), and USB carrying the
  FM-1's own samples unresampled, so a recording can be compared sample for sample with the same song
  rendered on a computer.

## 11. Tested first on the computer

Every scenario runs against the firmware compiled for the browser (the emulator's build, with the debug
build's figures), through MIRROR and the state query, every check passing, before it reaches the FM-1: a
wrong press shows there, not on the device.

## 12. Not in this proposal

- **A controller routed through a page, and the FM-1's sound to the computer's speakers:** the coming editor
  page's (a page editing instruments, songs and settings, loading and saving disks), with switchable
  profiles for outside controllers there.
- **The MIDI learn profiles** in the firmware.
