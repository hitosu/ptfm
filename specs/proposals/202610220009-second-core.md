# Proposal: the second core

Status: **settled** (2026-10-22). The AC791N has two cores; PT/FM has run on one. This proposal puts the effects
and the output stage on the second, keeps the voices and everything else on the first, and says how the second
starts, how it is switched, how it falls back, where its code lives, and how the screens and the debug build show
the two.

**Names.** On the screens and in the specs the cores are **core 1**, the one that runs everything today (the
interrupts, the main loop, every flash access, the voices), and **core 2**, the second. The chip numbers them 0
and 1 (its `cnum`); code that touches the chip says which numbering it uses.

## 1. Why

The sound runs out of CPU before it runs out of anything else. On the FM-1, DJ with two full decks (9.8 voices on
average, 12 at most) takes 87.7 % of a half on average, 95.9 % at the 95th percentile and 132 % in its worst half,
with 386 late halves in 30 s. Of a half: the voices 55 % (the Juno-106 35, the voices' mix 7.7, the Juno-106's
chorus 4.7, the DX7 1.8), the effects 24 % (REVERB 10.1, DELAY 4.2, DJ's mix of the decks 3.7, the punch-ins 2.0),
the control stages about 7 %. A song on DJ with a busier load runs at 64.8 %. Sixteen voices overran, so 12 is the
most.

The chip's second core runs at the same speed and is idle.

## 2. What the FM-1 showed

Measured on the FM-1 at the supplies the boot loader leaves (1.40 V, 1.26 V):

- **A late start works:** core 2 started from the main loop, the sound, the timers and USB running, interrupts off
  around the start: it answered in 0.41 µs, without the clock-divider bit the vendor's start sets (that bit is
  tried only if it does not answer).
- **A hand-over is cheap:** 1,000 empty jobs, a round trip 0.45 µs at least, 0.54 on average, 4.5 at most.
- **Core 2 is as fast as core 1, from RAM or from the flash:** a Juno-106 voice's 64-frame block 46.7 / 46.9 µs, a
  DX7 voice's 22.5 / 22.7, the REVERB's block 121.8 / 120.5. The code cache is shared: core 2's first runs of code
  core 1 ran come warm.
- **No contention:** core 1's pieces stay within ±1.3 % whatever core 2 runs (spinning, a stream through RAM, a
  Juno-106 voice or the REVERB from RAM or from the flash).
- **Core 2 runs on from RAM through core 1's direct flash reads:** 9,442 reads in 2 s with the code window off for
  each, no error on either side.
- **No misreads:** 5 minutes of core 2 checking a RAM pattern, a chain of numbers and a word core 1 writes, from RAM,
  with a song playing: 5.1 million rounds, none wrong; the sound clear.
- **A start after a hold fails:** core 2 faults in the chip's ROM it starts through, every time (contained: recorded,
  parked, held). **A restart of the chip clears that:** after a software restart, and after an update's restart,
  core 2 starts again. So core 2 starts once in each start of the firmware.
- **The ROM writes its own stack for core 2 at every start,** near 0x01C6FC70-0x01C6FF04.

## 3. What runs where

**Core 2 runs, for each block of 64 frames:**

- **the effects:** the block's events (the changes to the effects' own state the block made: a click, a punch-in,
  all sound off, CUT's emptying), its settings and its music clock put in place, then the effects' work on the
  block's mix and sends, or the rest path when the block is silent and the effects at rest
  ([../ui/screens/fx.md](../ui/screens/fx.md#effects-at-rest)). On DJ that is DJ's shared effects (CHORUS, DELAY,
  REVERB, LIMITER, the METRONOME) and the punch-ins;
- **the output stage:** the keys heard dry joined to the mix, CUT's fade, USB audio's stream (the mix at USB GAIN,
  resampled to the computer's clock), the soft ceiling, SYNC PULSE, VISUAL's ring, and the block converted into the
  codec's half (LINE GAIN, MASTER, mono).

**Core 1 keeps everything else:** the half's start (the requests, a chase's share, a deck's start made ready), each
block's control, the replays, the voices and their mix, DJ's decks' mix (each deck's own GATE, FILTER, DRIVE and
LO-FI, the DJ FILTERs, VOLUME and the crossfader), the music clocks, each block's copy of the effects' settings, MIDI;
and outside the sound, the main loop, every interrupt, every flash access, every peripheral.

**Core 2 reads and writes only RAM.** Its code, its constant tables and its stacks are in RAM ([section 8](#8-ram)),
so the flash's being busy (an erase, a program, a direct read) never touches it, and it is never held for it.

## 4. When: each block handed over as it is made

A half is four blocks. Core 1 makes block 0 up to its effects (its control, the replays, the voices, the clocks,
its copy of the settings) and hands it to core 2; while core 2 runs block 0's effects and output, core 1 makes
block 1, and so on. After the last block core 1 returns from the interrupt at once: the half being made plays only
after the one playing now has ended, 5.8 ms after the interrupt, so core 2 finishes the last block's effects and
output (about a fifth of a millisecond) long before the codec reaches it.

```
interrupt                                                    the codec reaches this half (5,804 µs)
|                                                                                      |
core 1  [start][block 0][block 1][block 2][block 3] (returns: the main loop runs)
core 2           [fx+out 0][fx+out 1][fx+out 2][fx+out 3]
```

- **First thing in the audio interrupt, core 1 makes sure core 2 has finished every block handed over before** (it
  has, but in an overload). Only then does core 1 change anything core 2 works on ([section 5](#5-who-owns-what)):
  the half to write into, the output's gains, USB audio's steering, the requests.
- **The same sound, sample for sample:** each block's effects run in order with the settings, the events and the
  clock that block had, as they do on one core block by block. The latency is the same.
- **On core 2 the effects take a block at a time.** On one core they take a half's four blocks together, each
  effect's code once ([../files/ram.md](../files/ram.md#where-the-ram-goes)), because code fetched from the flash
  costs; core 2's code is in RAM, where that saves nothing, and a block at a time is what lets core 2 start before
  the half's voices are all made.
- **CUT's halves run on core 1 alone,** as today: while CUT fades the sound out, each block's fade decides what the
  next block's voices feed the effects, so the blocks go one after another; faded out, the effects only keep time.
  Core 2 waits.
- **A late half** is one the codec reached before it was done: core 1's interrupt ran past it (as today), or core 2
  had not finished its last block when the next half began. The debug build counts them apart.

## 5. Who owns what

Every datum the sound uses belongs to one core at a time:

- **Handed over with a block** (its slot): the block's mix and sends, the keys' dry mix, the copy of the effects'
  settings, the music clock, the events, the block's flags (silent, sends, DJ's or the song's effects, SYNC PULSE's
  frame), and where in the codec's half it goes. Core 1 writes them before the hand-over and does not touch that slot again until core 2 has finished it.
  Flags that today live once for all blocks (whether the mix buffers still hold zeros from a block at rest) become
  per slot.
- **The effects' settings, live and working.** What the requests, the commands and the screens change (the effects
  on, their knobs, the chain, the routing, the METRONOME's, BYPASS, the forced DELAY / REVERB) is core 1's, the live
  settings; what the effects' work reads is a working copy, put in place from the block's copy at the start of each
  block's job. Core 1 never writes the working copy, core 2 never reads the live settings.
- **The effects' own state** (their lines, filters, LFOs, envelopes, the punch-in buffer, the METRONOME's click, the
  LIMITER's gain) is core 2's while it runs. Core 1 changes it only through a block's events, or at a half's start
  once core 2 has finished; a change that cannot wait for a block (the events' queue full) waits for core 2 first.
- **The output's state** (CUT's gain over the blocks, SYNC PULSE's count, VISUAL's place, USB audio's resampler and
  stream) is core 2's. USB audio's stream is a ring with one writer, core 2, and one reader, USB's interrupt on core
  1: the place moves only after the data are written, both published with the chip's sync.
- **What the main loop reads of core 2's** (the effects at work, the LIMITER's gain, GATE's step, FILTER's envelope,
  VISUAL's ring, the effects' times) it reads as it is, a word at a time: for the screens only, never to decide
  anything the sound depends on.
- **The main loop's locks** hold off the audio interrupt; they do not hold off core 2. A locked section that touches
  what core 2 works on also waits for core 2 to finish what it was handed. The store's and the edits' sections touch
  nothing of it; the effects' changes go through the requests, which the audio interrupt takes at a half's start.
  **The debug build's bench** runs its pieces on core 1 with no block handed over meanwhile; **the figures core 2
  counts** (its stages, its time) are its own, and their window is swapped by core 2 itself at a block's start when
  core 1 asks, so an answer never reads them half-counted.

## 6. The hand-over

A queue of a half's blocks in RAM: each entry its block and its number, and a check word made of both; core 1 writes
an entry, then the count of entries handed over; core 2 runs the next entry only when its number follows the last
one it finished and its check word matches, and writes the count it finished. Each core's words sit on a cache line
of their own. An entry whose check fails is a misread: core 2 counts it and leaves it ([section 7](#7-start-switch-fallback)).

Core 2 spins on the queue in its loop in RAM when it has nothing to do; it takes no interrupts.

## 7. Start, switch, fallback

- **The start:** 2 s into every start of the firmware (after a power-on, an update's restart or a crash's restart),
  with SECOND CORE on ([section 9](#9-screens)) and no crash with core 2 running recorded
  ([below](#a-crash)); from the main loop, interrupts off around it (under a microsecond). Core 2 starts through the
  chip's ROM, so the PC limits are opened for the start and armed again once it has answered from its loop in RAM;
  its entry word is written into the chip's top for the start and put back after. The clock-divider bit only on a
  second try, if it does not answer without it. Core 2 then sets its own stack limit.
- **Held only before a restart:** first thing at every start, and before every reset (the crash screen's, an update's,
  the chip's USB update mode, the debug build's watchdog test), with the safe hold: the bus traps off around it, the
  hold's own bus flag cleared. Never otherwise: a hold is final until the next start.
- **SECOND CORE, in SETTINGS, works at once both ways.** OFF: core 1 stops handing blocks over from the next half and
  runs the effects itself, as today; core 2 waits in its loop. ON: blocks are handed over again from the next half;
  if core 2 has not started yet in this start (SECOND CORE was off at the start), it starts then.
- **Fallbacks,** each ending this start's use of core 2:
  - **no answer** within 20 ms at the start (both tries);
  - **a misread:** an entry core 2 refused;
  - **stuck:** at a half's start, the blocks handed over in the half before not finished, and still not after 1 ms
    more (finished they are by then with well over a millisecond to spare);
  - **a fault:** core 2's exception keeps a record in its own RAM and parks it in its loop; core 1 sees it at the
    next half.

  A fallback holds core 2, and core 1 runs the effects from that half on: their state is all in RAM, so the sound
  goes on, at worst the blocks of one half lost (they play as silence). The toast `SECOND CORE STOPPED` once; STATUS' DEVICE page says why.
- <a id="a-crash"></a>**A crash with core 2 running:** the crash record says core 2 ran, and the starts that follow
  leave it off until the power goes off (the record lives in the RAM kept across restarts, which a power-off clears),
  so a fault it caused cannot loop. The boot guard is unchanged: two failed starts in a row end in the USB rescue; a
  crash core 2 caused counts once, and the next start, on one core, is healthy.
- **The supplies stay at the boot loader's levels.**

## 8. RAM

**Core 2's room** is a part of its own at the top of the RAM's data region, under the main loop's stack's guard
band, about 40 KB (the build says exactly):

- its code: the effects, the output stage, USB audio's stream writer, its loop, its fault handler's park, its own
  `memset` / `memcpy` and the timer read; and their constant tables, all copied from the image at power-on, as the
  flash driver's code is;
- its stacks: the jobs' (6 KB) and the exceptions' (1 KB), filled with a mark at each start (their depth);
- its queue, its counters and its fault record.

It is taken from the spare zone ([../files/ram.md](../files/ram.md#the-edit-memory-and-the-spare-zone)), whose 63 KB
floor was a cache's that is gone: the zone's own part becomes 24 KB, enough for what borrows from it (DJ's 13,116 B
and 3,840 more planned, USB audio's buffers' 6.5 KB in reserve), and the spare the build keeps stays (8 KB; 7 KB in
the debug build).

**Placed by what the chip does:**

- **its loop, its queue and its park lie at or above 0x01C72000,** where neither a restart nor the update loader
  writes, so a core 2 a reset did not hold would only spin there;
- **the ROM's start stack** (0x01C6F800-0x01C70000) **lies inside its jobs' stack,** which holds nothing at a start;
- **core 1's write limit covers its code** once copied, and **the PC limits' RAM window covers it.**

**The build checks** core 2's room: its code calls nothing outside it and names no flash address (code or data), no
instruction pair writes one register twice (the compiler was seen pairing a dead load with a live write of the same
register), it fits, its loop and queue lie above 0x01C72000, the ROM's start stack lies inside its jobs' stack, and
the zone keeps its floor. The stacks' worst case counts core 2's jobs' stack apart from the interrupts'.

## 9. Screens

**The header's CPU bar** ([../ui/frame.md](../ui/frame.md#the-header)) keeps its box, 4 × 10 at 217, 2, as two
columns of 2 px: core 1's at 217, core 2's at 219, each h = its share × 10, rounded, at least 1, each in the CPU
colours by its own share; the ground drawn whole. While core 2 is not running its column is the ground only. A late
half blinks both. **OVER 9000** when either core's mean over a second is above 90 %.

**SETTINGS** ([../ui/screens/settings.md](../ui/screens/settings.md)): **SECOND CORE**, after VOICES: ON / OFF, ON
by default (the footer `DEFAULT ON`), saved with the settings like the rest; the help's MORE SETTINGS page gains
`SECOND CORE: THE EFFECTS ON A 2ND CPU`.

**STATUS** ([../ui/screens/status.md](../ui/screens/status.md)):

- **The first page's figures:**
  ```
  CPU 1  23% MAX  41%  CPU 2  12% MAX  20%
  LATE    0            STEALS   0
  VOICES 06/12 MAX 09  HALF 1932 US
  RAM FREE 28K         EDITS FREE 32K
  FLASH FREE 237K      UNSAVED 3
  BATTERY 2/3          UP 01:23:45
  ```
  HALF moves to the third row's right (FPS's place), FPS to DEVICE. While core 2 is not running: `CPU 2  OFF`, dark
  grey.
- **PERFORMANCE:**
  ```
               NOW   AVERAGE     MOST
  CPU 1        23%       31%      41%
  CPU 2        12%       14%      20%
  WORST HALF  1932 US  LATE         0
  VOICES     06/09/12  STEALS       0
  ```
  then the engines, EFFECTS and the graph as before, 12 px lower; the graph's bars core 1's, core 2's a white line.
  While core 2 is not running its row reads `OFF`, dark grey.
- **DEVICE:** SCREEN FRAME shows the frames a second and the last frame's time (`12 FPS  31 MS`), and a new line
  **SECOND CORE**: `STARTING` (its first 2 s), `ON`, `OFF` (switched off), `STOPPED: NO ANSWER`, `STOPPED:
  MISREAD`, `STOPPED: STUCK`, `STOPPED: FAULT`, `STOPPED: AFTER A CRASH`.

**The CPU figures:** core 1's share is the audio interrupt's time over the half, as today (a wait for core 2 at a
half's start included); core 2's, its jobs' time over the half. MAX and MOST each core's own. HALF and WORST HALF are
core 1's interrupt.

**The settings record** ([../files/settings.md](../files/settings.md)): byte 123's bit 1 is SECOND CORE OFF, so a
record from before reads ON.

## 10. The debug build

- **FIGURES, version 11** ([../debug.md](../debug.md#the-figures)): every stage is measured wherever it runs, so on
  core 2 EFFECTS and its parts, OUTPUT and USB AUDIO; the audio interrupt's time is core 1's. A second message, **37
  FIGURES 2**, follows each 31 with core 2's window: its state and why it stopped, its jobs' time summed and its
  longest half, the blocks handed over, the misreads, core 1's waits for it at the halves' starts (summed and
  longest), the late halves each core caused, its jobs' stack's deepest point. The page joins the two by their
  window.
- **The page** shows both cores: CPU 1 and CPU 2, each with its mean, 95th percentile and worst; core 2's state; the
  graph with both; the report's lines with both.
- **AUTOTEST** runs with SECOND CORE as it is; **38 SECOND CORE** (page → device, one byte: 1 on, 0 off, as SETTINGS'
  switch, not saved) lets a scenario run with it off, so a run measures the same scenario on one core and on two.
- **PROVE** gains three actions, each ending in a fallback the page then reads: 4 core 2 faults on purpose, 5 a
  misread (an entry with a wrong check word), 6 core 2 stuck (a job that does not end).

## 11. The emulator and the playground

One core, the same sound. The emulator runs the same code: each block's job runs at once where it is handed over,
in the device's order, and its time counts as core 2's. The playground estimates core 2's share from the effects'
costs as it estimates the rest. Both show the two columns, the two CPU figures, SECOND CORE in SETTINGS (OFF moves
core 2's share back into core 1's) and DEVICE's line (`STARTING`, then `ON` or `OFF`; never `STOPPED`).

## 12. Not in this step

- **Voices on core 2** (the 12 voices split by cost, then perhaps more): after the FM-1's figures of this step.
- **Effects at the full rate** with the RAM left over.
- **Raised supplies.** The FM-1 showed no misread at the boot loader's levels.

## 13. Expected, to be measured on the FM-1

DJ with two full decks: about 1.1-1.2 ms of each half leaves core 1 (the effects but DJ's decks' mix, and the
output), so core 1 near 67 % on average instead of 87.7 %, core 2 near 20 %; the worst halves near the limit.
Measured by AUTOTEST (DJ HEAVY, DJ BUSY, KEYS at 12, IDLE) with SECOND CORE on and off, and a 30-minute run of DJ
with two full decks with the sound heard.
